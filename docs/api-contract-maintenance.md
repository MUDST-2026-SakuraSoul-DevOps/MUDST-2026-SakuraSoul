# สัญญา API ของงานซ่อมบำรุง (CR-05)

เอกสารนี้คือข้อตกลงระหว่างฝั่งหน้าเว็บกับฝั่ง Spring Boot ว่า endpoint ของงานซ่อมบำรุงหน้าตาเป็นแบบไหน
ครอบสี่ตั๋วของ epic CR-05 คือ SSK-18 (US-12 บันทึกงานซ่อม), SSK-19 (US-13 ประวัติซ่อมรายห้อง),
SSK-20 (US-14 แจ้งเตือนตามรอบ) และ SSK-23 (US-17 คลังอุปกรณ์)

เขียนสไตล์เดียวกับ [api-contract-lease.md](api-contract-lease.md) และใช้กฎร่วมกันทุกข้อ
error เป็น `ProblemDetail` ตาม RFC 9457 ข้อความที่เอาไปโชว์ผู้ใช้อยู่ในฟิลด์ `detail`

> **หมายเหตุ (SSK-105)** ข้อความใน `detail` ที่ backend ส่งกลับเป็นภาษาอังกฤษทั้งหมดแล้ว
> เพราะหน้าเว็บเปลี่ยนเป็นอังกฤษทั้งระบบ และจำนวนเงินทุกที่เป็นเยน (¥) ไม่มีทศนิยม
> ประโยคที่มีคู่ใน `frontend/src/domain/maintenanceBoard.ts` ต้องตรงกันเป๊ะ ห้ามเขียนใหม่เอง
วันที่เป็น `YYYY-MM-DD` เวลาเป็น ISO instant ชื่อฟิลด์เป็น camelCase และทุก endpoint ต้องล็อกอินก่อน

**ต่างจากสัญญาของ lease ตรงที่รอบนี้ฝั่ง backend ขึ้นก่อน** แท็บส่วนใหญ่ของ
`MaintenancePage.tsx` ยังเก็บข้อมูลไว้ใน `useState` ของหน้า (ยกเว้นแท็บ Maintenance Log
ที่ยิง `GET /api/maintenance` อยู่แล้ว) สิ่งที่ต้องแก้ฝั่งหน้าเว็บอยู่ในหัวข้อ
"สิ่งที่หน้าเว็บต้องเปลี่ยน" ท้ายเอกสาร

เทสที่บังคับสัญญานี้อยู่ฝั่ง backend คือ `MaintenanceApiTest`, `SupplyApiTest` และ `ReminderApiTest`
ถ้าจะแก้ข้อความหรือรูปร่างอะไรในเอกสารนี้ ต้องแก้เทสสามตัวนั้นพร้อมกันเสมอ

## ตารางที่เพิ่มเข้ามา

`V8__maintenance.sql` ห้าตารางในไฟล์เดียว เพราะสี่เรื่องนี้อ้างถึงกันเอง
(ใบแจ้งซ่อมตัดสต็อกอุปกรณ์ และการแจ้งเตือนตามรอบสร้างใบแจ้งซ่อม)

| ตาราง | เก็บอะไร |
| --- | --- |
| `maintenance_ticket` | ใบแจ้งซ่อมหนึ่งใบ ผูกกับห้องเสมอ |
| `supply_item` | ของหนึ่งรายการในคลังอุปกรณ์ |
| `supply_restock` | การเติมของเข้าคลังหนึ่งครั้ง (สมุดบันทึก ไม่ใช่ตัวเลขสรุป) |
| `maintenance_supply_usage` | ของที่ใช้ไปกับใบแจ้งซ่อมใบหนึ่ง |
| `maintenance_reminder` | การแจ้งเตือนตามรอบหนึ่งใบ |

สี่เรื่องที่ห้ามพลาด

- **สถานะสต็อกไม่ได้เก็บเป็นคอลัมน์** `LOW_STOCK` คำนวณจาก `stock < min_stock` ทุกครั้งที่ตอบ
  กฎเดียวกับ `supplyStatus` ใน `frontend/src/domain/maintenanceBoard.ts` ถ้าเก็บเป็นคอลัมน์
  แล้วมีคนแก้จำนวนโดยลืมแก้สถานะ ตารางจะโชว์ว่าของพอทั้งที่ต่ำกว่าขั้นต่ำแล้ว
- **สต็อกติดลบถูกกันสองชั้น** `supply_item_stock_ck` เป็นด่านสุดท้ายที่กันยอดติดลบไม่ให้ถูกเขียน
  ลงแถว แต่กันการเบิกซ้อนกันของสองคำขอไม่ได้ เพราะ Hibernate เขียนยอดใหม่ทั้งก้อน
  (`SET stock = 3`) ไม่ได้เขียนเป็นส่วนต่าง สองคนที่เบิกจากยอด 5 พร้อมกันจะอ่านได้ 5 ทั้งคู่
  แล้วเขียนทับกันโดยที่ยอดไม่เคยติดลบ ตัวกันเรื่องนั้นคือ **การล็อกแถวก่อนอ่าน**
  (`SupplyItemRepository.findForUpdateById` ใช้ทั้งตอนเบิกของและตอนเติมของ)
- **`maintenance_ticket.room_id` เป็น `NOT NULL`** ระบบนี้ไม่มีงานซ่อมที่ไม่สังกัดห้อง เพราะทั้ง
  US-12 และ US-13 พูดถึงงานซ่อม "ของห้อง" ถ้าวันหลังมีงานส่วนกลาง (ลิฟต์ ดาดฟ้า) ต้องเปิดให้
  เป็น `NULL` ได้ก่อน แล้วแก้ `RoomService` ที่เดียว
- **`maintenance_reminder.room_id` เป็น `NULL` ได้** เพราะงานอย่างล้างถังเก็บน้ำเป็นงานของทั้งตึก
  ผลของข้อนี้อยู่ในหัวข้อ "งานประจำวัน" ข้างล่าง

## Endpoint

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/maintenance` | ใบแจ้งซ่อมทั้งอพาร์ตเมนต์ ใบใหม่สุดขึ้นก่อน รับ query `status`, `roomId` |
| GET | `/api/maintenance/{id}` | ใบเดียว |
| POST | `/api/maintenance` | บันทึกงานซ่อม ตอบ 201 ของที่เบิกถูกตัดสต็อกในคำขอเดียวกัน |
| PATCH | `/api/maintenance/{id}` | แก้ทีละช่อง ตอบ 200 |
| DELETE | `/api/maintenance/{id}` | ลบใบที่เปิดผิด ตอบ **204** / 404 / **409** เมื่อไม่ใช่ `OPEN`, มาจากรอบแจ้งเตือน (`RECURRING`) หรือเบิกของไปแล้ว |
| POST | `/api/maintenance/{id}/supplies` | เบิกของเพิ่มให้ใบที่เปิดไว้แล้ว ตอบ 200 พร้อมใบทั้งใบ |
| GET | `/api/rooms/{id}/maintenance` | ประวัติซ่อมของห้องเดียว ใบใหม่สุดขึ้นก่อน / 404 ถ้าไม่มีห้องนี้ |
| GET | `/api/supplies` | คลังอุปกรณ์ทั้งหมด เรียงตามชื่อ |
| GET | `/api/supplies/summary` | ตัวเลขสามตัวบนหัวหน้าคลัง |
| POST | `/api/supplies` | เพิ่มอุปกรณ์ ตอบ 201 |
| PUT | `/api/supplies/{id}` | แก้อุปกรณ์ทั้งก้อน ตอบ 200 |
| POST | `/api/supplies/{id}/restock` | เติมของเข้าคลัง body `{ "quantity": 10 }` ตอบ 200 พร้อมของชิ้นนั้น |
| DELETE | `/api/supplies/{id}` | ลบของที่ยังไม่เคยถูกเบิก ตอบ **204** / 404 / **409** เมื่อเคยถูกเบิกในใบแจ้งซ่อมแล้ว (SSK-23) |
| GET | `/api/reminders` | การแจ้งเตือนตามรอบทั้งหมด เรียงวันครบกำหนดใกล้สุดก่อน |
| POST | `/api/reminders` | ตั้งการแจ้งเตือนใหม่ ตอบ 201 |
| PUT | `/api/reminders/{id}` | แก้ทั้งก้อน ตอบ 200 พร้อมวันครบกำหนดที่คิดใหม่แล้ว |
| PATCH | `/api/reminders/{id}/active` | เปิดปิดสวิตช์ body `{ "active": false }` ตอบ 200 เปิดกลับแล้วคิดวันครบกำหนดใหม่ (SSK-20) |
| DELETE | `/api/reminders/{id}` | ลบรอบที่ยังไม่เคยสร้างใบแจ้งซ่อม ตอบ **204** / 404 / **409** เมื่อเคยสร้างใบแล้ว (SSK-20) |
| POST | `/api/reminders/run-due` | สั่งให้ไล่ใบที่ถึงกำหนดเดี๋ยวนี้ ตอบ `{ "createdTickets": 1 }` |

**epic นี้ลบได้เฉพาะของที่ยังไม่มีประวัติ** คือใบแจ้งซ่อมที่เปิดผิด (SSK-131) ของในคลังที่ยังไม่เคยถูกเบิก
(SSK-23) และรอบแจ้งเตือนที่ยังไม่เคยสร้างใบแจ้งซ่อม (SSK-20) รอบแจ้งเตือนที่เคยสร้างใบแล้วแต่ไม่ใช้แล้วให้ปิดสวิตช์
และของในคลังที่เคยถูกเบิกไปแล้วแต่เลิกใช้ให้ตั้งจำนวนเป็นศูนย์ เหตุผลเดียวกับสัญญาเช่าคือประวัติเป็นข้อมูลที่หอพัก
ต้องเก็บ และของที่ลบไปแล้วจะทำให้ประวัติเก่าชี้ไปหาของที่ไม่มีอยู่

> **ข้อยกเว้น (25 ก.ย. 2569, SSK-131)** `DELETE /api/maintenance/{id}` ลบได้เฉพาะใบที่ยังไม่มี
> ประวัติอะไรเลย คือแอดมินกดสร้างผิดแล้วอยากเอาออก ต้องครบสามข้อ ไม่งั้นตอบ 409 พร้อมเหตุผล
>
> | ใบแบบนี้ | ตอบ | detail |
> | --- | --- | --- |
> | `IN_PROGRESS` | 409 | `This ticket is in progress and cannot be deleted. Only open tickets can be deleted.` |
> | `DONE` | 409 | `This ticket is done and is kept as maintenance history. It cannot be deleted.` |
> | มาจากรอบแจ้งเตือน (`source: RECURRING`) | 409 | `This ticket was created by a recurring reminder and cannot be deleted. Mark it as Done instead.` |
> | เบิกของไปแล้ว | 409 | `This ticket has supplies recorded against it and cannot be deleted. Mark it as Done instead.` |
> | ไม่มีใบนี้ | 404 | `No maintenance ticket with id 999` |
>
> ตรวจตามลำดับในตาราง ลบสำเร็จตอบ **204 ไม่มี body** หน้าเว็บเรียกผ่าน `requestNoContent`
> แบบเดียวกับลบห้องและผู้เช่า (ดู api-contract-lease.md หัวข้อลบห้องและผู้เช่า)
>
> ใบ `RECURRING` ลบไม่ได้แม้ยัง `OPEN` เพราะใบนั้นคือหลักฐานว่ารอบแจ้งเตือนทำงานแล้ว `run-due`
> เลื่อน `nextDueDate` ไปรอบถัดไปตั้งแต่ตอนสร้างใบ ถ้าลบทิ้ง รอบนั้นจะไม่ถูกสร้างใหม่ งานซ่อมตามรอบ
> หายไปเงียบ ๆ ให้ปิดเป็น `DONE` แทน
>
> ใบที่เบิกของไปแล้วลบไม่ได้ เพราะสต็อกถูกตัดไปแล้ว ถ้าลบใบ ประวัติการเบิกจะชี้ไปหาใบที่ไม่มีอยู่

## ใบแจ้งซ่อม (US-12, US-13)

ก้อนที่ตอบกลับจากทุก endpoint ของใบแจ้งซ่อม

```json
{
  "id": 12,
  "roomId": 1,
  "roomNumber": "101",
  "title": "แอร์ไม่เย็น",
  "detail": "ห้องนอนแอร์ไม่เย็นตั้งแต่เมื่อวาน",
  "status": "OPEN",
  "reportedAt": "2026-10-08T03:00:00Z",
  "maintenanceType": "แอร์",
  "priority": "HIGH",
  "assignedTo": "ช่างสมศักดิ์",
  "reportedBy": "ยูกิ ทานากะ",
  "scheduledDate": "2026-10-09",
  "cost": 850.50,
  "source": "MANUAL",
  "closedAt": null,
  "suppliesUsed": [
    { "supplyId": 3, "name": "หลอดไฟ LED", "quantity": 2 }
  ]
}
```

**เจ็ดฟิลด์แรกคือ `MaintenanceTicket` ใน `frontend/src/api/types.ts` ทั้งชุดและเรียงลำดับเดียวกัน**
หน้าเว็บที่อ่านแค่เจ็ดฟิลด์นั้นอยู่แล้วใช้ได้ทันทีโดยไม่ต้องแก้อะไร ที่เหลือเป็นของเพิ่มของ CR-05

- `status` เป็น `OPEN` / `IN_PROGRESS` / `DONE`
- `priority` เป็น `LOW` / `MEDIUM` / `HIGH` / `URGENT` ไม่ส่งมาตอนสร้างถือว่า `MEDIUM`
- `source` เป็น `MANUAL` (แอดมินกดเปิดเอง) หรือ `RECURRING` (ระบบสร้างจากการแจ้งเตือนตามรอบ)
- `closedAt` มีค่าเฉพาะใบที่สถานะเป็น `DONE` การเปิดใบกลับมาใหม่จะล้างค่านี้ทิ้ง
- `cost` เป็น `NUMERIC(10,2)` ปัดแบบ HALF_UP ชุดเดียวกับเงินก้อนอื่นทั้งระบบ เป็น `null` ได้
- `suppliesUsed` เป็นลิสต์ว่างเมื่อยังไม่ได้เบิกของ ไม่ใช่ `null`

body ของ `POST /api/maintenance`

```json
{
  "roomId": 1,
  "title": "แอร์ไม่เย็น",
  "detail": "ห้องนอนแอร์ไม่เย็นตั้งแต่เมื่อวาน",
  "maintenanceType": "แอร์",
  "priority": "HIGH",
  "assignedTo": "ช่างสมศักดิ์",
  "reportedBy": "ยูกิ ทานากะ",
  "scheduledDate": "2026-10-09",
  "cost": 850.5,
  "suppliesUsed": [{ "supplyId": 3, "quantity": 2 }]
}
```

บังคับแค่ `roomId` กับ `title` ที่เหลือไม่บังคับทั้งหมด

body ของ `PATCH /api/maintenance/{id}` รับเก้าช่องคือ `status`, `assignedTo`, `priority`,
`scheduledDate`, `cost`, `detail`, `title`, `maintenanceType`, `reportedBy`
**ช่องที่ไม่ส่งมาแปลว่าไม่แก้ ไม่ได้แปลว่าให้ล้างค่า**

> **อัปเดต SSK-131** เพิ่ม `title`, `maintenanceType`, `reportedBy` เพราะฟอร์ม Edit Task ให้แก้สามช่องนี้
> อยู่แล้ว (แก้คำพิมพ์ผิดหลังสร้างใบ) `title` ส่งมาเป็นช่องว่างตอบ 400 `Please enter the task title`
> ประโยคเดียวกับตอนสร้าง ส่วน `maintenanceType` กับ `reportedBy` ส่ง `""` มาแปลว่าล้างค่าแบบเดียวกับ
> `assignedTo` **ห้องแก้ไม่ได้** (`roomId` ที่ส่งมาถูกมองข้าม) เพราะย้ายใบข้ามห้องทำให้ประวัติซ่อม
> ของทั้งสองห้องผิด ใบที่เปิดผิดห้องให้ลบแล้วสร้างใหม่

**ส่ง `"assignedTo": ""` (หรือช่องว่างล้วน) มาแปลว่าถอนการมอบหมาย** ใบจะเก็บเป็น `null`
แล้วกลับไปขึ้นป้าย Wait for Assign ตามตารางเทียบป้ายข้างล่าง ที่ต้องมีทางถอนเพราะฟอร์มแก้ไข
ในดีไซน์ปล่อยให้ช่องนี้ว่างได้ ถ้าไม่มีทางล้าง ใบที่เคยมอบหมายไปแล้วจะติดชื่อช่างคนเดิมตลอดไป
ส่วน `scheduledDate`, `cost` และ `detail` ยังล้างค่าไม่ได้ (ส่ง `null` มาถือว่าไม่แก้) ถ้าหน้าจอ
ต้องการจริงค่อยตกลงรูปแบบกันอีกที
ที่เป็น PATCH ไม่ใช่ PUT เพราะหน้าจอจริงแก้ทีละอย่าง (ลากการ์ดเปลี่ยนสถานะ กดมอบหมายให้ช่าง)
การบังคับส่งใบทั้งก้อนกลับมาจะทำให้หน้าเว็บเขียนทับช่องที่คนอื่นเพิ่งแก้ไปโดยไม่ได้ตั้งใจ

### การตัดสต็อกอัตโนมัติ (US-12-S1)

ส่ง `suppliesUsed` มาพร้อมตอนสร้างใบ หรือยิง `POST /api/maintenance/{id}/supplies` ทีหลังก็ได้
ทั้งสองทางทำงานเหมือนกันเป๊ะ คือหักจำนวนออกจาก `supply_item.stock` แล้วบันทึกแถวใน
`maintenance_supply_usage` ว่าใบไหนใช้อะไรไปเท่าไหร่

**ทุกอย่างอยู่ใน transaction เดียวกับการบันทึกใบ** ของไม่พอสักชิ้นเดียวก็ย้อนกลับทั้งใบ
ไม่มีทางที่จะได้ใบแจ้งซ่อมที่บันทึกไว้แล้วแต่สต็อกไม่ถูกตัด หรือกลับกัน

### ปิดใบแจ้งซ่อม ≠ ปลดล็อกห้อง

**การปิดใบแจ้งซ่อมไม่ไปแตะธง `under_maintenance` ของห้องเลย** และการปลดล็อกห้องก็ไม่ไปปิด
ใบแจ้งซ่อมเช่นกัน สองเรื่องนี้แยกกันโดยตั้งใจ

การล็อกห้องเป็นซ่อมบำรุงเป็นการตัดสินใจของแอดมินตาม US-15 (`PATCH /api/rooms/{id}/status`)
ว่าห้องนี้ปล่อยเช่าไม่ได้ ส่วนใบแจ้งซ่อมเป็นรายการงานที่ต้องทำ ห้องหนึ่งมีงานค้างได้หลายใบ
ถ้าปิดใบหนึ่งแล้วห้องถูกปลดล็อกให้เอง ห้องที่แอดมินตั้งใจปิดไว้ซ่อมใหญ่จะถูกเปิดคืนเพราะงานย่อย
งานหนึ่งเสร็จ ซึ่งไม่ใช่สิ่งที่ผู้ใช้สั่ง

### สองฟิลด์บนการ์ดห้อง

`GET /api/rooms` กับ `GET /api/rooms/{id}` ส่งสองฟิลด์นี้มาตั้งแต่ก่อน CR-05 แล้วแต่ยังเป็นค่าว่าง
ตอนนี้มีค่าจริงแล้ว **รูปร่าง JSON ไม่เปลี่ยน หน้าเว็บไม่ต้องแก้อะไร**

- `openMaintenanceCount` คือจำนวนใบของห้องนั้นที่สถานะยังไม่ใช่ `DONE`
- `openMaintenanceTitle` คือ `title` ของใบที่ค้างอยู่และ **แจ้งไว้นานที่สุด** เป็น `null` เมื่อไม่มีใบค้าง
  (ไม่ใช่ใบล่าสุด เฟรม Dashboard ใน Figma โชว์ข้อความนี้บนการ์ดห้อง 104 กับ 201)

ทั้งหน้าผังห้องใช้คิวรีเดียวสำหรับเรื่องนี้ ไม่ใช่ห้องละคิวรี ถ้าจะแก้ `RoomService` ทีหลัง
ต้องรักษาข้อนี้ไว้ ไม่งั้นการโหลดแดชบอร์ดครั้งเดียวจะกลายเป็น 24 คิวรี

## คลังอุปกรณ์ (US-17)

```json
{
  "id": 3,
  "name": "หลอดไฟ LED",
  "sku": "BULB-01",
  "category": "ไฟฟ้า",
  "stock": 12,
  "minStock": 5,
  "maxStock": 20,
  "status": "IN_STOCK",
  "createdAt": "2026-10-08T03:00:00Z"
}
```

- `status` เป็น `LOW_STOCK` เมื่อ `stock < minStock` นอกนั้นเป็น `IN_STOCK`
  **เท่ากับขั้นต่ำพอดียังนับว่าพอ** กฎเดียวกับฝั่งหน้าเว็บ
- `maxStock` คือเพดานที่ควรมีของในคลัง (เพิ่มใน SSK-23 ตาม BUG-M6 ของ SSK-111 ที่ QA ขอ) **บังคับกรอก**
  ต้องไม่น้อยกว่า `minStock` และ `stock` ต้องไม่เกิน `maxStock` ทั้งตอนสร้าง ตอนแก้ และหลังเติมของ
  เท่ากับเพดานพอดียังรับได้ เพดานมีไว้กันการสั่งของเกินความจำเป็น ถ้าของล้นเพดานจริงต้องไปขยับเพดานก่อน
  ไม่ใช่ปล่อยให้สองตัวเลขนี้ขัดกันเองอยู่ในตาราง
- `sku` ส่งมาเป็น `null` หรือช่องว่างล้วนได้ **server ออกรหัสให้เอง** (SSK-23) เป็นสองอักษรละตินแรกของหมวด
  ตัวพิมพ์ใหญ่ ต่อด้วย `-` และ id เติมศูนย์ให้ครบสามหลัก เช่น `Plumbing` ชิ้นที่ 4 ได้ `PL-004`
  หมวดที่ไม่มีอักษรละตินเลยได้ `XX` (สูตรเดียวกับที่หน้าเว็บเคยออกให้เองก่อนต่อ API)
  ถ้ารหัสที่ได้ไปชนกับรหัสที่มีคนพิมพ์ไว้ ระบบต่อท้าย `-2`, `-3` ไปเรื่อย ๆ จนไม่ชน
  รหัสที่กรอกมาเองยังต้องไม่ซ้ำเหมือนเดิม ที่ต้องออกให้เพราะตารางหน้าเว็บโชว์ SKU ทุกแถว
  และฟอร์มไม่มีช่อง SKU ให้พิมพ์ ตอนแก้ของ หน้าเว็บส่งรหัสเดิมกลับมาใน `PUT`
- `maxStock` เก็บในคอลัมน์ `max_stock` ที่เพิ่มใน `V13__supply_max_stock.sql` ของที่มีอยู่ก่อนแล้ว
  ได้เพดานเป็นสองเท่าของค่าที่มากกว่าระหว่าง `stock` กับ `min_stock` ยังเติมของต่อได้ทันที
  ฐานเดิมไม่ต้อง `docker compose down -v` เพื่อให้ได้คอลัมน์นี้ กฎทั้งสามข้อของเพดานมี CHECK ใน V13
  เป็นด่านสุดท้ายเหมือน `supply_item_stock_ck` (`supply_item_max_stock_ck`, `supply_item_min_max_ck`,
  `supply_item_stock_max_ck`) ส่วนข้อความที่ผู้ใช้เห็นมาจาก `SupplyItem` ที่ตรวจก่อนเขียน

body ของ `POST` และ `PUT` เหมือนกัน คือ `name`, `sku`, `category`, `stock`, `minStock`, `maxStock`

**การเติมของ** รับ `quantity` เป็นจำนวนเต็มบวกเท่านั้น ส่ง `2.5` มาได้ 400 `The restock amount must be a whole number`
ไม่ถูกปัดเป็น 2 เงียบ ๆ (ของนับเป็นชิ้น) ส่วน `2.0` นับเป็น 2 และยอดหลังเติมต้องไม่เกิน `maxStock`

**การลบ (SSK-23)** `DELETE /api/supplies/{id}` ลบได้เฉพาะของที่ **ยังไม่เคยถูกเบิกในใบแจ้งซ่อมเลย** คือแอดมินเพิ่มผิด
แล้วอยากเอาออก ประวัติการเติมของชิ้นนั้น (`supply_restock`) ถูกลบไปด้วย เพราะเป็นประวัติของของที่ไม่ควรมีอยู่ตั้งแต่แรก
ของที่เคยถูกเบิกแล้วตอบ 409 `This item has been used in maintenance tickets and cannot be deleted. Set its stock to 0 instead.`
เพราะใบแจ้งซ่อมเก่ายังต้องบอกได้ว่าใช้อะไรไป ลบสำเร็จตอบ **204 ไม่มี body** การลบล็อกแถวของชิ้นนั้นก่อนเช็ค
(`SupplyItemRepository.findForUpdateById` ตัวเดียวกับที่การเบิกใช้) การเบิกที่เข้ามาพร้อมกันจึงแทรกระหว่าง
"เช็คว่ายังไม่เคยเบิก" กับ "ลบ" ไม่ได้

`GET /api/supplies/summary`

```json
{ "totalItems": 12, "lowStockItems": 3, "restockedThisWeek": 40 }
```

`restockedThisWeek` คือ **ผลรวมจำนวนชิ้นที่เติม** ไม่ใช่จำนวนครั้งที่กดเติม นับจากแถวใน
`supply_restock` ที่เกิดในเจ็ดวันปฏิทินล่าสุดตามเวลาไทย (ตั้งแต่เที่ยงคืนของหกวันก่อนจนถึงตอนนี้)
ที่นับเป็นวันปฏิทินไม่ใช่ 168 ชั่วโมงถอยหลัง เพราะแอดมินที่เปิดดูตอนเย็นคาดหวังว่าของที่เติมเมื่อเช้า
ของเจ็ดวันก่อนยังนับอยู่

**`PUT` ตั้งจำนวนใหม่ได้ตรง ๆ แต่ห้ามใช้แทนการเติมของ** เพราะการเติมต้องทิ้งรอยไว้ใน
`supply_restock` ให้การ์ดข้างบนนับได้ ทางที่ถูกคือ `POST /api/supplies/{id}/restock`
ส่วน `PUT` ไว้แก้ตอนนับสต็อกจริงแล้วไม่ตรงกับในระบบ

การค้นหาไม่มี endpoint เพราะ US-17-S4 ระบุว่าเป็นการกรองรายการที่โหลดมาแล้วฝั่งหน้าเว็บ
ของในคลังของหอขนาดนี้มีหลักสิบถึงร้อยรายการ ส่งทั้งชุดไปให้กรองเองเร็วกว่ายิงถามทุกตัวอักษรที่พิมพ์

## แจ้งเตือนตามรอบ (US-14)

```json
{
  "id": 4,
  "name": "ล้างแอร์ทุกไตรมาส",
  "frequency": "QUARTERLY",
  "startDate": "2026-01-31",
  "nextDueDate": "2026-04-30",
  "overdue": false,
  "roomId": 1,
  "roomNumber": "101",
  "remindTime": "09:00",
  "priority": "HIGH",
  "notes": "ล้างคอยล์และเปลี่ยนไส้กรอง",
  "active": true,
  "lastTriggeredAt": "2026-01-31T01:00:00Z"
}
```

- `frequency` เป็น `ONE_TIME` / `MONTHLY` / `QUARTERLY` / `ANNUAL`
  (ตัวพิมพ์ใหญ่ ต่างจาก `One-time` / `Monthly` / `Quarterly` / `Annual` ฝั่งหน้าเว็บ ต้องแปลงตอนส่ง)
- `nextDueDate` ของใบที่เพิ่งสร้างเท่ากับ `startDate` เสมอ **ไม่ได้ถูกเลื่อนให้เอง** เพราะแอดมินที่
  ตั้งวันเริ่มย้อนหลังตั้งใจบอกว่า "งานนี้ควรทำไปแล้ว" ใบจึงต้องขึ้นเป็นเลยกำหนดทันที
- `overdue` คือ `nextDueDate < วันนี้` (เวลาไทย) server คิดให้เพราะ "วันนี้" ของเครื่องผู้ใช้กับของ
  server อาจคนละวันถ้าตั้งโซนเวลาต่างกัน แล้วป้ายเลยกำหนดจะไม่ตรงกัน
- `roomId` / `roomNumber` เป็น `null` ได้ แปลว่าเป็นงานของทั้งตึก (ช่อง unit ในดีไซน์)
- `remindTime` เป็นสตริง `HH:MM` หรือ `null` ตอนนี้เป็นข้อมูลให้คนอ่าน ยังไม่เปลี่ยนเวลาที่ระบบยิงจริง

body ของ `POST` และ `PUT` คือ `name`, `frequency`, `startDate`, `roomId`, `remindTime`,
`priority`, `notes` — บังคับ `name`, `frequency` และ `startDate`

**`PUT` คิด `nextDueDate` ใหม่ทุกครั้งจาก `startDate` กับ `frequency` ชุดใหม่เทียบกับวันนี้**
ด้วยสูตรเดียวกับ `nextOccurrence` ใน `frontend/src/domain/maintenanceBoard.ts` คือเดินทีละก้าว
จนกว่าจะถึงหรือเลยวันนี้ ที่ต้องคิดใหม่เพราะการเปลี่ยนวันเริ่มหรือรอบทำให้ค่าเดิมไม่มีความหมาย
(ย้ายจากรายเดือนเป็นรายปีแล้ววันครบกำหนดยังเป็นเดือนหน้าอยู่ ใบจะยิงผิดรอบ)
ใบที่ปิดสวิตช์ไว้ถือว่าตารางหยุดเดิน `nextDueDate` ค้างอยู่ที่ `startDate` เหมือนฝั่งหน้าเว็บ

**แต่ `PUT` จะไม่ดึง `nextDueDate` ย้อนกลับไปทับรอบที่ระบบยิงใบไปแล้ว** สูตรที่คิดสด ๆ คืนค่า
"วันนี้" เมื่อวันนี้ตรงกับรอบพอดี ใบรายเดือนที่เริ่ม 15 ม.ค. ซึ่งงานประจำวันยิงไปแล้วเมื่อเช้าของ
วันที่ 15 ก.พ. ถ้าแอดมินมาแก้บันทึกตอนบ่าย `nextDueDate` จะถูกดึงกลับมาเป็น 15 ก.พ. แล้ว
รอบถัดไปจะสร้างใบแจ้งซ่อมซ้ำให้รอบเดิม จึงเทียบกับ `lastTriggeredAt` (ตามวันเวลาไทย) แล้ว
เดินต่ออีกก้าวเมื่อรอบที่คิดได้ถูกยิงไปแล้ว ผลคือได้ 15 มี.ค. ตามเดิม

**พักกับเปิดกลับ (SSK-20)** `PATCH /{id}/active` ส่ง `false` แค่ปิดสวิตช์ ไม่แตะช่องอื่น ส่ง `true` แล้ว
**คิด `nextDueDate` ใหม่ด้วยสูตรเดียวกับ `PUT`** คือรอบแรกที่ยังไม่เลยวันนี้และไม่ซ้ำรอบที่ยิงไปแล้ว รอบที่พลาด
ไประหว่างพักจึงถูกข้าม ไม่ใช่เด้งกลับมาเป็นเลยกำหนดแล้วสร้างใบแจ้งซ่อมย้อนหลังให้รอบที่ไม่มีใครรอแล้ว
(เดิมเปิดกลับแล้ว `nextDueDate` ค้างค่าเก่า ถ้าพักแล้วแก้ใบ ค่าจะเป็น `startDate` ซึ่งอาจเป็นรอบที่ยิงไปแล้ว
ดูหัวข้อ "งานประจำวัน")

ใบ `ONE_TIME` ที่ยิงไปแล้วเปิดกลับไม่ได้ ได้ 409
`This one-time reminder already ran on 2026-09-01. Change its start date before resuming it.`
เพราะรอบเดียวของมันทำไปแล้ว ถ้าอยากให้ทำอีกครั้ง ให้แก้วันเริ่มเป็นวันหลังจากวันที่ยิง (`PUT` ระหว่างที่ยังพักอยู่)
แล้วค่อยเปิด

**การลบ (SSK-20)** `DELETE /api/reminders/{id}` ลบได้เฉพาะรอบที่ **ยังไม่เคยสร้างใบแจ้งซ่อม** คือตั้งผิดแล้วอยากเอาออก
รอบที่เคยสร้างใบแล้วได้ 409 `This reminder has already created maintenance tickets and cannot be deleted. Pause it instead.`
เพราะใบแจ้งซ่อมเก่าชี้กลับมาที่รอบนี้ (`maintenance_ticket.reminder_id`) ลบสำเร็จตอบ **204 ไม่มี body**
การลบล็อกแถวของรอบนั้นก่อนเช็ค (`MaintenanceReminderRepository.findForUpdateById`) งานประจำวันที่ยิงพร้อมกัน
จึงสร้างใบแทรกระหว่าง "เช็คว่ายังไม่มีใบ" กับ "ลบ" ไม่ได้ รอบของทั้งตึกไม่เคยสร้างใบแจ้งซ่อม จึงลบได้เสมอ

### การบวกเดือนต้องหนีบวันสิ้นเดือน

31 ม.ค. บวกหนึ่งเดือนต้องได้ **28 ก.พ.** (หรือ 29 ในปีอธิกสุรทิน) ไม่ใช่ล้นไปเป็น 3 มี.ค.
ฝั่ง backend ใช้ `LocalDate.plusMonths` ซึ่งหนีบให้เอง ตรงกับ `addMonths` ฝั่งหน้าเว็บที่หนีบด้วย
วันสุดท้ายของเดือนปลายทาง

และทั้งสองฝั่งเดิน **ทีละก้าว** ไม่ได้คำนวณจำนวนก้าวทีเดียว เพราะการหนีบทำให้ก้าวแต่ละก้าว
ไม่เท่ากัน (31 ม.ค. → 28 ก.พ. → 28 มี.ค. → 28 เม.ย.) ถ้าฝั่งไหนเปลี่ยนไปคำนวณทีเดียว
วันครบกำหนดของสองฝั่งจะเริ่มต่างกันเงียบ ๆ

### งานประจำวัน

ทุกเช้า **08:00 ตามเวลาไทย** (`@Scheduled(cron = "0 0 8 * * *", zone = "Asia/Bangkok")`)
ระบบจะไล่ใบแจ้งเตือนที่ถึงกำหนด แล้วทำสามอย่างกับใบที่ยิง

1. สร้างใบแจ้งซ่อมให้หนึ่งใบ โดย `source` เป็น `RECURRING`, `title` = ชื่อใบแจ้งเตือน,
   `detail` = `notes`, `scheduledDate` = วันครบกำหนดที่ยิง, สถานะ `OPEN`
2. บันทึก `lastTriggeredAt`
3. เลื่อน `nextDueDate` ไปข้างหน้าทีละก้าวจน **พ้นวันนี้** ส่วนใบ `ONE_TIME` ปิดสวิตช์แทน

เงื่อนไขที่ทำให้ใบถูกยิงคือ `active = true` **และ** `nextDueDate <= วันนี้` ใบที่ปิดสวิตช์ไว้
ถูกข้ามถึงจะเลยกำหนดมานานแล้วก็ตาม

ที่ต้องเลื่อนให้ "พ้นวันนี้" ไม่ใช่แค่ "ถึงวันนี้" เพราะการรันซ้ำในวันเดียวกัน (แอดมินกดปุ่มเอง
หรือ pod ที่รีสตาร์ต) จะสร้างใบซ้ำไปเรื่อย ๆ การเรียก `POST /api/reminders/run-due` ซ้ำ
ในวันเดียวกันจึงปลอดภัย ครั้งที่สองได้ `createdTickets` เป็น 0

**รอบที่มีใบแจ้งซ่อมอยู่แล้วไม่ถูกสร้างซ้ำ (SSK-20)** ก่อนสร้างใบ ระบบเช็คว่ามีใบของรอบนั้น
(`reminder_id` + `scheduled_date`) อยู่แล้วหรือยัง ถ้ามีจะข้ามการสร้าง แต่ยังจดเวลาและเลื่อนรอบตามปกติ
เดิมไม่มีด่านนี้ ถ้าแอดมินพักรอบ แก้ใบ (ใบที่พักอยู่ `nextDueDate` จะกลับไปที่ `startDate`) แล้วเปิดกลับ
หรือเปิดใบ `ONE_TIME` ที่ยิงไปแล้ว รอบเดิมจะถูกยิงซ้ำไปชน unique index `maintenance_ticket_reminder_due_uk`
งานประจำวันทั้งชุดอยู่ใน transaction เดียวจึงถูก rollback ทั้งหมด **ทุกวัน** รอบอื่นทุกใบก็ไม่ได้ใบแจ้งซ่อมไปด้วย
ตอนนี้กันไว้สองชั้น คือการเปิดกลับคิดวันใหม่ (หัวข้อข้างบน) และด่านนี้ใน `ReminderService.runDue`

### สอง pod ยิงงานประจำวันพร้อมกัน

k8s รัน backend **สอง pod** อยู่จริง (`replicas: 2` ใน `k8s/20-backend.yaml`) งานแปดโมงเช้า
จึงยิงพร้อมกันสองที่ในวินาทีเดียวกัน ตัวกันใบซ้ำไม่ใช่ข้อตกลงว่าจะรันชุดเดียว แต่เป็นสองชั้นที่
ฐานข้อมูล

1. **ล็อกแถวใบแจ้งเตือนตอนอ่าน** (`SELECT ... FOR UPDATE` ผ่าน
   `MaintenanceReminderRepository.findDueForUpdate`) pod ที่สองรอจนตัวแรก commit แล้ว
   PostgreSQL เอาเงื่อนไข `next_due_date <= วันนี้` มาตรวจแถวที่ล็อกได้ใหม่อีกรอบ ตอนนั้นวัน
   ครบกำหนดถูกเลื่อนพ้นวันนี้ไปแล้ว ใบจึงหลุดออกจากผลลัพธ์เอง
2. **unique index `maintenance_ticket_reminder_due_uk`** บน `(reminder_id, scheduled_date)`
   เฉพาะแถวที่มี `reminder_id` เป็นด่านสุดท้าย ถ้าหลุดมาถึงจะได้ 409
   `A ticket for this reminder cycle has already been created` ไม่ใช่ 500

ใบที่แอดมินเปิดเอง (`source` เป็น `MANUAL`) ไม่ติด index ตัวนี้ ห้องเดียวกันวันเดียวกันจะเปิด
กี่ใบก็ได้

**การแจ้งเตือนของ US-14 ออกมาเป็นใบแจ้งซ่อมที่โผล่ในระบบ ไม่ใช่อีเมลหรือ push** เพราะโจทย์
ของวิชาห้ามพึ่ง external service และสิ่งที่แอดมินต้องทำต่อจริง ๆ คือไปจัดการงานซ่อมใบนั้น
ไม่ใช่แค่รับรู้ว่าถึงรอบแล้ว

**ใบที่ไม่ได้ระบุห้องยังไม่สร้างใบแจ้งซ่อมให้** เพราะ `maintenance_ticket.room_id` เป็น `NOT NULL`
แต่ยังเลื่อนรอบให้ตามปกติ ไม่งั้นใบจะค้างเป็นเลยกำหนดตลอดไปและถูกหยิบมาพิจารณาใหม่ทุกวัน
ข้อนี้จะหายไปเองวันที่เปิดให้ใบแจ้งซ่อมไม่สังกัดห้องได้ ระหว่างนี้ถ้าอยากให้ยิงจริงต้องเลือกห้องให้ใบ

สี่จุดที่ชื่อค่าสองฝั่งไม่ตรงกัน ต้องแปลงตอนรับส่ง

1. **สถานะงาน** หน้าเว็บใช้ `'In Progress' | 'Pending' | 'Wait for Assign'` ส่วน API ใช้สามค่าของ
   สัญญานี้ ตารางเทียบที่ตกลงกันคือ

   | ป้ายบนหน้าจอ | ค่าใน API |
   | --- | --- |
   | Wait for Assign | `OPEN` |
   | Pending | `OPEN` |
   | In Progress | `IN_PROGRESS` |
   | Done (เพิ่มใน SSK-131) | `DONE` |

   สองป้ายแรกต่างกันแค่ว่ามีคนรับงานหรือยัง ซึ่งดูจาก `assignedTo` ได้ตรง ๆ อยู่แล้ว
   **ให้เลิกเก็บเป็นสถานะแยก** แล้วคำนวณป้ายจาก `status` + `assignedTo` แทน คือ
   `status === 'OPEN' && assignedTo == null` ขึ้น Wait for Assign นอกนั้นขึ้น Pending
   ส่วน `DONE` ต้องเพิ่มป้ายใหม่ (ดีไซน์เดิมไม่มี เพราะหน้าจอเดิมไม่มีวิธีปิดงาน)

2. **ชื่อฟิลด์ของงานซ่อม** `task` → `title`, `unit` (เลขห้อง) → `roomId` + `roomNumber`,
   `assignTo` → `assignedTo`, `reportBy` → `reportedBy`, `date` → `scheduledDate`
   ช่อง `unit` ที่เป็นเลขห้องต้องหา `roomId` จากรายการห้องก่อนส่ง เพราะฝั่ง API ผูกเป็น
   foreign key จริง (`validateMaintenanceTask` ที่เช็คว่าเลขห้องเป็นตัวเลขสามหลักยังใช้ได้
   เป็นด่านแรก แต่ด่านจริงคือห้องนั้นมีอยู่ในระบบไหม)

3. **ระดับความสำคัญกับรอบ** `'Low' | 'Medium' | 'High' | 'Urgent'` ↔ `LOW` / `MEDIUM` / `HIGH` /
   `URGENT` และ `'One-time' | 'Monthly' | 'Quarterly' | 'Annual'` ↔ `ONE_TIME` / `MONTHLY` /
   `QUARTERLY` / `ANNUAL` เขียนตัวแปลงคู่เดียวไว้ใน `src/api/` แล้วใช้ร่วมกันทุกหน้า

4. **`nextOccurrence` กับ `supplyStatus` ไม่ต้องคำนวณเองแล้ว** API ส่ง `nextDueDate`, `overdue`
   และ `status` ของอุปกรณ์มาให้ครบ ให้ใช้ค่าจาก API เป็นหลักเพื่อไม่ให้สองฝั่งคิดคนละอย่าง
   ฟังก์ชันเดิมยังเก็บไว้ได้สำหรับพรีวิวตอนกรอกฟอร์มก่อนกดบันทึก และเทสของมันยังมีค่าอยู่
   เพราะเป็นตัวยืนยันว่าสูตรสองฝั่งตรงกัน

`ExportLogButton` ของ SSK-24 ถูกวางไว้บนหัวแท็บ Maintenance Log เรียบร้อยแล้ว และรับรายการ
**ที่กรองแล้ว** ตาม US-18-S2 ไม่มีอะไรต้องต่อเพิ่มจากฝั่งนี้

### แท็บ Maintenance Tasks (SSK-131)

- ตัวแปลงอยู่ที่ `src/api/maintenanceMappers.ts` ตามข้อ 3 ข้างบน ฟอร์มกับตารางยังใช้
  `MaintenanceTask` ใน `maintenanceBoard.ts` เป็นโมเดลของหน้าจอ ไม่ต้องรื้อ dialog
- ฟอร์ม Edit Task มีช่อง **Status** (Open / In Progress / Done) ฟอร์มสร้างไม่มี เพราะใบใหม่เป็น
  `OPEN` เสมอ **ช่องห้องล็อกตอนแก้** เพราะ PATCH ไม่รับ `roomId`
- ใบที่ปิดเป็น `DONE` ยังอยู่ในตาราง Tasks พร้อมป้าย Done ไม่หายไปเฉย ๆ
- **ปุ่มลบ** เรียก `DELETE` ใบที่ลบไม่ได้จะเห็นเหตุผลจาก 409 ในป็อปอัปยืนยัน
- **วันนัดล้างไม่ได้** เพราะ PATCH ถือว่าช่องที่ไม่ส่งคือไม่แก้ ฟอร์มแก้งานจึงเตือน
  `The date cannot be removed once set. Pick another date instead.` แทนที่จะปล่อยให้วันเดิม
  กลับมาเงียบ ๆ หลังบันทึก และกด Confirm โดยไม่ได้แก้อะไรจะไม่ยิง PATCH เลย
- **ป้ายในแท็บ Log** ใช้ `taskStatusOf` ตัวเดียวกับแท็บ Tasks ใบ `OPEN` ที่มีช่างขึ้น Pending
  ตรงกันทั้งสองแท็บ (เดิมแท็บ Log ขึ้น Wait for Assign ให้ใบ `OPEN` ทุกใบ) ต่างกันแค่ `DONE`
  ที่แท็บ Log ใช้คำว่า Completed ตามเฟรม Maintenance log
- **Bill to tenant / Amount (SSK-134) ↔ `cost`** ไม่มีคอลัมน์แยก เพราะช่อง Amount กรอกได้เฉพาะตอน
  ติ๊ก Bill to tenant และต้องมากกว่าศูนย์ สองช่องจึงเทียบเท่า `cost > 0` พอดี
  ส่งไป: `cost = billToTenant ? amount : null` (ตอนแก้ส่ง `0` แทน `null` เพราะ PATCH ล้างค่าไม่ได้)
  อ่านกลับ: `amount = cost ?? 0`, `billToTenant = cost > 0` ถ้าวันหลังใบเสร็จต้องดึงค่าซ่อมไปเก็บ
  ผู้เช่าจริง ค่อยเพิ่มคอลัมน์ธงแยกพร้อมกันทีเดียว
  ตอนนี้ค่าซ่อม**ยังไม่เข้าบิล** เพราะใบเสร็จมีห้ารายการตายตัว (ดู `api-contract-billing.md`
  หัวข้อ "ที่ยังไม่มีในเฟสนี้") ข้อความใต้ช่องในป็อปอัปทั้งสองจึงบอกว่าบันทึกไว้ในใบแจ้งซ่อมเท่านั้น
  เดิมเขียนว่าจะเพิ่มบรรทัด Repair charge ในบิลเดือนถัดไป ซึ่งไม่จริง (SSK-144)

### Create Maintenance บน Dashboard (SSK-131)

| ช่องในฟอร์ม | ส่งเป็น |
| --- | --- |
| Unit | `roomId` หาจากรายการห้องที่โหลดไว้แล้วด้วยเลขห้อง |
| Maintenance Type | `maintenanceType` **และใช้เป็น `title` ด้วย** เพราะฟอร์มนี้ไม่มีช่องชื่องาน และชื่อจะไปขึ้นบนการ์ดของห้องนั้นอยู่แล้ว จึงไม่ต้องต่อเลขห้อง แก้ชื่อทีหลังได้ที่แท็บ Tasks |
| Notes | `detail` (ว่างส่ง `null`) |
| Bill to tenant + Amount | `cost` ตามกฎข้างบน |
| Out of service | สร้างใบก่อน แล้วค่อย `PATCH /api/rooms/{id}/status` เป็น `MAINTENANCE` ลำดับนี้กันกรณีล็อกห้องได้แต่สร้างใบไม่สำเร็จ |
| Recurring | ✅ **เปิดใช้ใน SSK-20** (SSK-131 ปิดไว้จนกว่าแท็บ Schedule & Reminder จะต่อ API) สร้างใบแจ้งซ่อมก่อน แล้วสร้างรอบแจ้งเตือนด้วย `POST /api/reminders` ชื่อ = ประเภทงาน, `frequency` จาก Repeat every, `startDate` = Next maintenance date, `roomId` = ห้องที่เลือก, `notes` = Notes, ไม่ตั้งเวลา |

**Repeat every เหลือ Monthly / Quarterly / Annual** ตัด `Every 6 months` ออก เพราะ backend ไม่มีรอบนี้
และ **Next maintenance date ต้องอยู่หลังวันนี้** (`The next maintenance date must be after today`) ใบแจ้งซ่อมที่เพิ่งเปิด
คืองานของวันนี้อยู่แล้ว ถ้าให้รอบเริ่มวันนี้ งานประจำวันพรุ่งนี้จะสร้างใบของวันนี้ซ้ำอีกใบ

สร้างใบไม่สำเร็จ ป็อปอัปค้างไว้และโชว์ `detail` ของ backend ข้อมูลที่กรอกไม่หาย ถ้าสร้างใบได้แต่ล็อกห้อง
ไม่สำเร็จ ป็อปอัปบอกว่าใบถูกสร้างแล้วและให้ไปล็อกที่หน้า Units แทน กันผู้ใช้กดบันทึกซ้ำจนได้ใบซ้ำ
ถ้าสร้างใบได้แต่สร้างรอบแจ้งเตือนไม่สำเร็จ ป็อปอัปบอกแบบเดียวกันว่าใบถูกสร้างแล้ว และให้ไปตั้งรอบที่แท็บ
Schedule & Reminder แทน

### แท็บ Supplies & Inventory (SSK-23)

- โหลด `GET /api/supplies` กับ `GET /api/supplies/summary` พร้อมกันใน loader ตัวเดียว ทุกครั้งที่เพิ่ม แก้ เติม
  หรือลบสำเร็จจะโหลดทั้งสองใหม่ ตารางกับการ์ดจึงไม่มีทางเห็นตัวเลขคนละชุดกัน
- การ์ดสามใบใช้ตัวเลขจาก summary ทั้งหมด **RECENT RESTOCKS คือ `restockedThisWeek`** (จำนวนชิ้นที่เติม
  ในเจ็ดวันล่าสุด คำอธิบายใต้ตัวเลขคือ `Units restocked in the last 7 days`) เดิมนับจำนวนครั้งที่กดในรอบที่เปิดแอป
  ซึ่งรีเฟรชแล้วหาย ส่วนคำว่า `Across N categories` ใต้ TOTAL ITEMS นับหมวดจากรายการที่โหลดมา
- ป้าย In Stock / Low Stock ใช้ `status` ของ API ตามข้อ 4 ข้างบน `supplyStatus` ยังอยู่ให้เทสยืนยันว่าสูตรสองฝั่งตรงกัน
- ฟอร์มไม่มีช่อง SKU ตอนเพิ่มส่ง `sku: null` ให้ server ออกรหัส ตอนแก้ส่งรหัสเดิมกลับไป
- ฟอร์มเพิ่ม/แก้ ฟอร์มเติมของ และป็อปอัปยืนยันลบ รอคำตอบจาก API ก่อนปิด error จาก backend (เช่น 409
  ของที่เคยถูกเบิกแล้ว) ขึ้นในป็อปอัปนั้นเลย ไม่ปิดไปเฉย ๆ
- `mockApi.ts` เดินตามกฎและข้อความของ backend ทุกข้อ รวมถึงการออก SKU การรวมยอดเติมเจ็ดวันตามวันไทย
  และ 409 ตอนลบของที่ใบแจ้งซ่อมเบิกไปแล้ว (ใบห้อง 106 ใน mock เบิก Air Filters ไป 1 ชิ้น)

### แท็บ Schedule & Reminder (SSK-20)

- โหลด `GET /api/reminders` ในแท็บ การ์ดใช้ `nextDueDate` กับ `overdue` ของ server ตามข้อ 4 ข้างบน
  ไม่ได้คิดเองจาก `nextOccurrence` แล้ว รอบที่พักอยู่ขึ้นป้าย Paused
- ปุ่ม ⋮ บนการ์ดเป็นเมนู **Edit** (`PUT` ผ่านฟอร์มเดียวกับ Add Reminder) **Pause / Resume** (`PATCH active`)
  และ **Delete** (`DELETE` รอบที่เคยสร้างใบแจ้งซ่อมแล้วได้ 409 ที่บอกให้ Pause แทน ขึ้นในป็อปอัปยืนยัน)
  error ของ Pause / Resume (เช่น 409 ของใบ ONE_TIME ที่ยิงไปแล้ว) ขึ้นใต้รายการ
- ช่อง Assigned Unit มีตัวเลือก **All units (building-wide)** ส่ง `roomId: null` พร้อมคำอธิบายใต้ช่องว่า
  รอบของทั้งตึกขึ้นในรายการกับปฏิทิน แต่ไม่สร้างใบแจ้งซ่อม (ดูหัวข้องานประจำวัน) ไม่เลือกอะไรเลยยังได้
  `Please choose the unit` เหมือนเดิม
- **ปฏิทินรายสัปดาห์** เลิกใช้ `WEEK_EVENTS` ตายตัว (ที่มี Unit 305 ซึ่งไม่มีจริง) แสดงของจริงสองอย่าง
  1. รอบแจ้งเตือนที่เปิดอยู่ซึ่งตรงกับวันจันทร์ถึงศุกร์ของสัปดาห์นี้ คิดจาก `startDate` กับ `frequency` ด้วยการเดินทีละก้าว
     แบบเดียวกับ `nextOccurrence` (ใบ `ONE_TIME` มีวันเดียวคือวันเริ่ม) วางตาม `remindTime` (ไม่ได้ตั้งใช้ 09:00)
     ยาวหนึ่งชั่วโมง ใต้ชื่อบอก `Unit 104` หรือ `All units` ที่คิดจากวันเริ่ม ไม่ใช้ `nextDueDate` เพราะค่านั้นถูกเลื่อน
     ไปรอบหน้าทันทีที่งานแปดโมงเช้ายิง รอบของวันนี้จะหายจากปฏิทินตั้งแต่เช้า
  2. ใบแจ้งซ่อมที่แอดมินเปิดเอง (`MANUAL`) ซึ่งนัดวันไว้ในสัปดาห์นี้ เป็นชิปในแถบใต้หัววัน เพราะใบแจ้งซ่อมมีแค่วันที่
     ไม่มีเวลา ใบ `RECURRING` ไม่ขึ้นซ้ำ เพราะรอบแจ้งเตือนของมันขึ้นอยู่แล้ว
- `mockApi.ts` ทำตัวเหมือน `ReminderService` ทุกข้อ รวมถึงการเปิดกลับที่คิดวันใหม่ 409 ทั้งสองแบบ และ `run-due`
  ที่มีด่านกันใบซ้ำ

### วันที่ของ `reportedAt` (Today's Activity และไฟล์ Export Log)

`reportedAt` เป็นเวลาแบบ ISO (`2026-09-25T03:12:00Z`) ต้องเทียบเป็น**วันตามเวลาไทย**
(`dateInBangkok` ใน `format.ts`) เดิมเทียบสตริงตรง ๆ กับวันนี้ จึงได้ศูนย์เสมอเมื่อต่อ backend จริง
ตัดสิบตัวแรกเฉย ๆ ก็ไม่ได้ เพราะใบที่แจ้งตั้งแต่เที่ยงคืนถึงก่อนเจ็ดโมงเช้าตามเวลาไทยเป็นวันใหม่แล้วในไทย
แต่ยังเป็นวันก่อนหน้าใน UTC คอลัมน์ Reported ของไฟล์ Export Log ใช้วันไทยแบบเดียวกัน (`YYYY-MM-DD`)
เดิมใส่เวลาเต็มแบบ UTC ลงไฟล์ตรง ๆ

## ของที่ยังไม่ได้ตกลง

- **การเช่าเครื่องใช้ไฟฟ้า (appliance rental)** ยังไม่มีใครนิยามว่าคืออะไรในระบบนี้ หน้า
  `AppliancesPage.tsx` เป็นเฟรม "Appliance Rental" ของ Figma ตรง ๆ คือรายการขอเช่าของ
  (ตู้เย็น เครื่องซักผ้า) ที่มีค่าเช่า วันเริ่ม และสถานะ Active / Pending / Returned ซึ่ง **CR-05
  ไม่ได้ทำและยังไม่มี endpoint ให้สักตัว** จะเป็นคนละตารางและต้องผูกกับสัญญาเช่า ต้องถาม
  เจ้าของ requirement ก่อน ยังไม่ควรเดาแล้วทำไปก่อน
  (คลังอุปกรณ์ซ่อมที่ CR-05 ทำเสร็จอยู่ในแท็บ Supplies & Inventory ของ `MaintenancePage.tsx`
  คนละที่กับหน้านี้ อย่าสลับกัน)
- **`remindTime` ยังไม่มีผลกับเวลาที่ระบบยิงจริง** งานประจำวันยิงรอบเดียวตอนแปดโมงเช้า
  ถ้าจะให้เตือนตามเวลาที่ตั้งจริงต้องเปลี่ยน scheduler เป็นรอบถี่กว่านี้แล้วเทียบเวลาด้วย
  ซึ่งยังไม่มี requirement ข้อไหนขอ
- **ยังไม่มีตัวล็อกร่วมอย่าง ShedLock และตอนนี้ยังไม่จำเป็น** งานประจำวันทำงานซ้ำได้โดยไม่เกิด
  ผลซ้ำแล้ว (ล็อกแถว + unique index ดูหัวข้อ "สอง pod ยิงงานประจำวันพร้อมกัน") ถ้าวันหลังมี
  งานประจำวันที่ซ้ำไม่ได้จริง ๆ เช่น ส่งอีเมลหรือตัดเงิน ค่อยใส่ตัวล็อกร่วม
