# สัญญา API ของการรับชำระ ยอดยกมา ดอกเบี้ย บัญชีรับเงิน การพิมพ์รวม และรายงาน (Phase 2)

เอกสารนี้ครอบการ์ด SSK-163 (รับชำระบางส่วนและหนี้ค้าง), SSK-164 (ยกยอดค้างและดอกเบี้ย),
SSK-168 (บัญชีรับเงินและ QR PromptPay), SSK-169 (พิมพ์ใบเสร็จรวม) และ SSK-170 (รายงานสรุป)
หน้าเว็บของการ์ดเหล่านี้ทำเสร็จแล้วแต่เก็บข้อมูลไว้ในเบราว์เซอร์ (localStorage) เอกสารนี้จึงเขียน **ก่อน**
ฝั่ง Spring ลงมือ เพื่อให้หน้าเว็บเริ่มเปลี่ยนไปเรียก API ได้พร้อมกับที่ backend ทำ

**สถานะ:** 163+164 ทำแล้วใน #222 (migration V21 ต่อจาก V20 ของ SSK-171) ที่เหลือวางไว้คือ 168 (V22) → 169 → 170
endpoint กับกฎในเอกสารนี้ถือเป็นข้อตกลงแล้ว จุดที่ backend ทำต่างไปจดไว้ใน `docs/api-contract-phase2-backend.md`
(ไฟล์นั้นมากับ PR ของโค้ดตั้งแต่ #210 ซึ่งยังไม่มีเอกสารนี้ จึงแก้ในไฟล์นี้ตรง ๆ ไม่ได้)

กฎทั้งหมดมาจากข้อสรุปในคอมเมนต์ Jira ของทีมวันที่ 7 พ.ย. (SSK-163, SSK-164, SSK-168)
และสิ่งที่เจ้าของ backend ตัดสินเพิ่มวันที่ 10 พ.ย. ซึ่งทำเครื่องหมาย **(10 พ.ย.)** ไว้ตรงที่ใช้

## หลักการ

1. **จ่ายที่ใบล่าสุดของสัญญาเท่านั้น** ใบเก่าที่ยังค้างถูกยกยอดมารวมในใบใหม่ทุกครั้งที่ออกใบ ผู้เช่าจึงมีบิลที่ต้องจ่ายใบเดียวเสมอ
2. **ระบบตัดยอดเองแบบ FIFO** เงินที่รับมาตัดยอดค้างของใบเก่าสุดก่อน แล้วค่อยไล่มาถึงใบปัจจุบัน
   ภายในใบเดียวกันตัด **ดอกเบี้ยก่อนแล้วค่อยต้นเงิน (10 พ.ย.)** ตามลำดับเริ่มต้นใน ป.พ.พ. มาตรา 329
3. **ดอกเบี้ยแบบง่าย** คิดจากต้นเงินคงเหลือเท่านั้น ไม่คิดดอกเบี้ยซ้อนจากดอกเบี้ย ปัดครึ่งขึ้นเหลือสองตำแหน่ง
4. **ของที่ตกลงไว้แล้วไม่เปลี่ยนตาม** อัตราดอกเบี้ยกับวันผ่อนผันเป็นของสัญญา (คัดลอกตอนเซ็น) และบัญชีรับเงินเป็นของใบเสร็จ (คัดลอกตอนออก)
   แก้ค่าในหน้า Apartment settings ทีหลังจึงมีผลกับสัญญาและใบเสร็จที่ทำหลังจากนั้นเท่านั้น หลักการเดียวกับ US-16-S3 และ SSK-180
5. **ตัวเลขของใบเสร็จถูกเก็บไว้ตั้งแต่ตอนออก** ส่งอีเมลซ้ำ ดาวน์โหลด PDF ซ้ำ หรือเปิดรายงานวันไหนก็ได้ยอดยกมากับดอกเบี้ยเท่าเดิม

## Endpoint

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/receipts`, `/api/receipts/{id}` | เหมือนเดิม แต่ใบเสร็จมีฟิลด์ใหม่ และกรอง `status=PARTIAL` ได้ |
| POST | `/api/receipts` | เหมือนเดิม แต่คิดยอดยกมาและดอกเบี้ยให้ ดูหัวข้อ "ยกยอดและดอกเบี้ย" |
| PUT | `/api/receipts/{id}` | เหมือนเดิม (SSK-155) แต่แก้ได้เฉพาะใบล่าสุดที่ยังไม่มีการชำระ |
| POST | `/api/receipts/{id}/payments` | บันทึกการรับชำระ (บางส่วนหรือเต็มจำนวน) ตอบ 201 |
| GET | `/api/receipts/{id}/payments` | รายการการชำระที่บันทึกบนบิลใบนี้ |
| POST | `/api/payments/{id}/void` | ยกเลิกการชำระ ตอบ 200 |
| POST | `/api/receipts/{id}/pay` | **ของเดิมยังใช้ได้** หมายถึงรับชำระเต็มยอดที่ต้องจ่ายในครั้งเดียว |
| GET | `/api/debts` | หนี้ค้างของแต่ละสัญญา พร้อมจำนวนวันที่เกินกำหนดและช่วงอายุหนี้ |
| PUT | `/api/apartment-config/late-interest` | ตั้งอัตราดอกเบี้ยกับวันผ่อนผันสำหรับสัญญาใหม่ |
| PUT | `/api/apartment-config/bank-account` | ตั้งบัญชีรับเงินและ PromptPay สำหรับใบเสร็จใหม่ |
| POST | `/api/receipts/print` | ใบเสร็จหลายใบเป็น PDF ไฟล์เดียว |
| GET | `/api/reports/summary` | รายงานสรุปตามห้อง ผู้เช่า หรือเดือน |
| GET | `/api/reports/summary.csv` | รายงานเดียวกันเป็นไฟล์ CSV |

ทุกตัวต้องล็อกอินก่อนเหมือน endpoint อื่นทั้งระบบ
ค่าตั้งใหม่ทั้งสองชุดแยกเป็น PUT ของตัวเอง ไม่รวมกับ `PUT /api/apartment-config` เดิม เพราะ PUT เดิมแทนค่าทั้งแถว
ฟอร์มอัตราค่าน้ำค่าไฟที่ส่งแค่สี่ช่องจะลบค่าใหม่ทิ้งทุกครั้งที่กดบันทึก

ตัวอย่างใช้เรื่องเดียวกับ Jira ตลอดทั้งเอกสาร
- ใบเดือนตุลาคม (RC-2026-0011) ค่าใช้จ่าย 5,000.00 รับชำระไปแล้ว 2,000.00 ยังค้าง 3,000.00
- ออกใบเดือนพฤศจิกายน (RC-2026-0012) วันที่ 1 ธ.ค. ยอดค้างของตุลาคมถูกยกมา คิดดอกเบี้ย 1.5% ต่อเดือน

### ยอดของใบ แยกเป็นสองมุม

ใบหนึ่งใบมีตัวเลขสองมุม และต้องไม่ปนกัน

**มุมบิล** คือสิ่งที่พิมพ์อยู่บนกระดาษที่ผู้เช่าถือ

| ฟิลด์ | ความหมาย |
| --- | --- |
| `chargesAmount` | ค่าใช้จ่ายของเดือนนี้ คือห้าบรรทัดเดิมรวมกับค่าใช้จ่ายพิเศษของ SSK-165 |
| `previousBalance` | ยอดค้างของใบก่อนหน้าทุกใบของสัญญาเดียวกัน (ต้นเงิน + ดอกเบี้ยที่ยังค้าง) ณ ตอนออกใบนี้ แช่แข็งไว้ |
| `interestAmount` | ดอกเบี้ยที่คิดในใบนี้ ดูหัวข้อ "ยกยอดและดอกเบี้ย" |
| `totalAmount` | `chargesAmount + previousBalance + interestAmount` เท่ากับผลรวมของ `items` เสมอ<br>ใบที่ออกก่อน Phase 2 ไม่มีสองยอดใหม่ ตัวเลขจึงเท่าเดิม |
| `paidAmount` | ผลรวมการชำระที่บันทึก **บนบิลใบนี้** และยังไม่ถูกยกเลิก เงินก้อนนี้อาจถูกตัดเข้าใบเก่าก็ได้ |
| `balanceDue` | ยอดที่ยังต้องจ่ายตามบิลนี้ `totalAmount - paidAmount` **มีค่าเฉพาะใบล่าสุด** ใบอื่นเป็น `null` |

**มุมของใบเอง** คือค่าใช้จ่ายและดอกเบี้ยที่เกิดในใบนี้ ถูกตัดไปแล้วเท่าไหร่ ไม่สนว่าเงินถูกบันทึกบนบิลใบไหน

| ฟิลด์ | ความหมาย |
| --- | --- |
| `settledAmount` | เงินที่ระบบตัดเข้าค่าใช้จ่ายกับดอกเบี้ยของใบนี้แล้ว (จากการชำระครั้งไหนก็ได้) |
| `outstandingAmount` | `chargesAmount + interestAmount - settledAmount` ไม่รวมยอดยกมา<br>**จะรวมยอดค้างหลายใบให้ใช้ฟิลด์นี้** รวมแล้วไม่นับซ้ำ |
| `status` | จากมุมของใบเอง ทุกใบใช้กฎเดียวกัน: `PAID` เมื่อ `outstandingAmount` เป็น 0, `PARTIAL` เมื่อตัดไปบางส่วน, `PENDING` เมื่อยังไม่ถูกตัดเลย |

ตัวอย่างข้างบน รับ 3,000.00 บนใบพฤศจิกายนแต่เงินถูกตัดเข้าใบตุลาคมทั้งก้อน
- ใบตุลาคมกลายเป็น `PAID` (`settledAmount` 5,000.00) ทั้งที่ `paidAmount` ของมันเองคือ 2,000.00
- ใบพฤศจิกายนยังเป็น `PENDING` (`settledAmount` 0.00) ทั้งที่ `paidAmount` คือ 3,000.00
- หน้าเว็บอยากโชว์ว่าบิลนี้รับเงินไปแล้วเท่าไหร่ ให้ใช้ `paidAmount` กับ `balanceDue` ส่วนป้ายสถานะใช้ `status`
- **สถานะไม่เปลี่ยนเพราะการยกยอดเฉย ๆ** เปลี่ยนเมื่อมีเงินถูกตัดหรือถูกยกเลิกเท่านั้น

**ฟิลด์อื่น**

| ฟิลด์ | ความหมาย |
| --- | --- |
| `latest` | `true` ถ้าเป็นใบล่าสุดของสัญญา (`billingMonth` มากสุด) ปุ่มรับชำระมีเฉพาะใบนี้ |
| `oldestUnpaidDueDate` | เฉพาะใบล่าสุด: วันครบกำหนดของใบเก่าสุดที่ยังมี `outstandingAmount` เหลือ ไม่มีหนี้เป็น `null` |
| `overdue` | เฉพาะใบล่าสุด: `true` เมื่อ `balanceDue > 0` และวันนี้ (เวลาไทย) เลย `oldestUnpaidDueDate` แล้ว ใบอื่นเป็น `false`<br>หนี้เก่าที่ถูกยกมาจึงยังขึ้นเกินกำหนดอยู่ ไม่หายไปตอนออกใบใหม่ |
| `carriedToReceiptId` | ใบที่ยอดค้างถูกยกไปอยู่ในบิลอื่นแล้ว เป็น id ของบิลล่าสุดที่รวมยอดนี้ไว้ ใบอื่นเป็น `null` |
| `payments` | การชำระที่บันทึกบนบิลใบนี้ เรียงตามเวลาที่บันทึก รวมรายการที่ถูกยกเลิกด้วย (`voidedAt` ไม่เป็น `null`) |
| `bank` | สำเนาบัญชีรับเงิน ณ วันที่ออกใบ ถ้าตอนนั้นยังไม่ได้ตั้งบัญชีเป็น `null` |
| `promptPayPayload` | ข้อความ EMV ของ QR PromptPay ที่ใส่ `balanceDue` ไว้แล้ว เป็น `null` เมื่อไม่ใช่ใบล่าสุด, `balanceDue` เป็น 0 หรือใบนี้ไม่มี PromptPay ID |
| `paidAt`, `paymentMethod` | ฟิลด์เดิม ยังส่งมาเพื่อไม่ให้หน้าเว็บที่อ่านอยู่พัง<br>`paidAt` คือเวลาที่บันทึกการชำระที่ทำให้ใบนี้เป็น `PAID`<br>`paymentMethod` คือช่องทางของการชำระครั้งนั้นเป็นข้อความอ่านได้ (`Cash`, `Bank transfer`, `PromptPay QR`, `Other`) หรือข้อความที่ส่งมากับ `/pay` แบบเดิม |

บรรทัด `Previous balance` ใส่เลขที่ของใบที่ถูกยกมาไว้ใน `detail` ถ้ามีหลายใบคั่นด้วย `, `

## รับชำระ

### POST /api/receipts/{id}/payments

```json
{
  "amount": 3000.00,
  "paidOn": "2026-12-01",
  "method": "TRANSFER",
  "reference": "KBANK 0012",
  "note": null
}
```

- `amount` ต้องมากกว่า 0 และไม่เกิน `balanceDue` ปัดเหลือสองตำแหน่งแบบครึ่งขึ้นก่อนตรวจ
- `paidOn` คือวันที่ได้รับเงินจริง รูปแบบ `YYYY-MM-DD` ไม่ส่งมาให้เป็นวันนี้ตามเวลาไทย ห้ามเป็นวันในอนาคต
- `method` บังคับ เป็นหนึ่งใน `CASH`, `TRANSFER`, `QR`, `OTHER`
  หน้าเว็บตอนนี้ใช้ `'Cash'`, `'Bank transfer'`, `'PromptPay'` ให้แปลงเป็น `CASH`, `TRANSFER`, `QR`
- `reference` (เลขอ้างอิงจากธนาคาร ไม่เกิน 100 ตัว) กับ `note` (ไม่เกิน 500 ตัว) ไม่บังคับ
- **บันทึกได้เฉพาะบนใบล่าสุดของสัญญา** ส่งมาที่ใบเก่าได้ 409 พร้อมเลขที่ของใบที่ถูกต้อง
- ลำดับการตรวจ: ไม่พบใบ (404) → ไม่ใช่ใบล่าสุด (409) → จ่ายครบแล้ว (409) → ค่าในคำขอผิด (400) → เกินยอด (400)
- ตอบ 201 เป็นบิลใบนี้หลังตัดยอด
  **การตัดยอดเปลี่ยนสถานะของใบเก่าในสัญญาเดียวกันด้วย** (ตามตัวอย่าง ใบตุลาคมกลายเป็น `PAID`)
  หน้าเว็บจึงต้องโหลด `GET /api/receipts?leaseId=…` ใหม่ ไม่ใช่แก้แค่แถวเดียว
- **สลิปโอนเงิน** ไม่ส่งมากับคำขอนี้ ให้บันทึกการชำระก่อน แล้วอัปโหลดสลิปด้วย `POST /api/attachments`
  `ownerType=PAYMENT` และ `ownerId` = id ของการชำระที่ได้กลับมา (ดู [api-contract-documents.md](api-contract-documents.md))

### ระบบตัดยอดอย่างไร

เงินหนึ่งก้อนถูกตัดตามลำดับนี้จนหมด
1. ใบที่ยังมี `outstandingAmount` ของสัญญานี้ เรียงจากเดือนเก่าสุดไปถึงใบล่าสุด
2. ภายในแต่ละใบ ตัดดอกเบี้ยที่ใบนั้นคิดไว้ก่อน แล้วค่อยตัดค่าใช้จ่าย (ต้นเงิน)

ระบบเก็บว่าเงินแต่ละก้อนตัดใบไหนไปเท่าไหร่ แยกดอกเบี้ยกับต้นเงิน การยกเลิกจึงคืนยอดได้ตรงทุกสตางค์ และดอกเบี้ยครั้งถัดไปคิดจากต้นเงินที่เหลือจริง

| ขั้น | ใบตุลาคม (RC-…0011) | ใบพฤศจิกายน (RC-…0012) |
| --- | --- | --- |
| ก่อนออกใบพฤศจิกายน | `settledAmount` 2,000.00, `outstandingAmount` 3,000.00, `PARTIAL` | ยังไม่มี |
| ออกใบพฤศจิกายน | ถูกยกไป RC-…0012 (`carriedToReceiptId` 12) ตัวเลขเดิม | `totalAmount` 8,145.00 = 5,100 + 3,000 + 45, `balanceDue` 8,145.00, `PENDING` |
| รับชำระ 3,000.00 บนใบพฤศจิกายน | `settledAmount` 5,000.00, `PAID` | `paidAmount` 3,000.00, `balanceDue` 5,145.00, ยัง `PENDING` |
| ยกเลิกการชำระนั้น | กลับไป `outstandingAmount` 3,000.00, `PARTIAL` | `paidAmount` 0.00, `balanceDue` 8,145.00 |

### POST /api/receipts/{id}/pay (ของเดิม)

ยังใช้ได้ หมายถึงรับชำระเท่ากับ `balanceDue` ทั้งหมดในครั้งเดียว กฎเดียวกับ `/payments` คือใช้ได้กับใบล่าสุดเท่านั้น
- `paymentMethod` ที่ส่งมาเป็นข้อความอิสระถูกเก็บไว้ใน `note` ของการชำระ ช่องทางถูกบันทึกเป็น `OTHER`
- `paymentMethod` ของใบเสร็จจึงยังเป็นข้อความเดิมที่ส่งมา อีเมลแบบ "Paid on … (Cash)" ยังอ่านเหมือนเดิม

หน้าเว็บใหม่ควรเปลี่ยนไปใช้ `POST /api/receipts/{id}/payments` เพื่อระบุช่องทางให้ถูก

### POST /api/payments/{id}/void

ไม่มี body ตอบ 200 เป็นบิลที่การชำระนั้นอยู่ หลังคืนยอดแล้ว (ใบเก่าเปลี่ยนตามด้วย ให้โหลดรายการของสัญญาใหม่เหมือนตอนรับชำระ)

ยกเลิกได้เฉพาะ **การชำระล่าสุดของสัญญาที่ยังไม่ถูกยกเลิก** และบิลที่บันทึกไว้ต้องยังเป็นใบล่าสุด (ยังไม่ถูกยกยอดไปบิลใหม่)
- การคืนยอดย้อนหลังทีละก้อนจากล่าสุดทำให้ทุกยอดกลับไปตรงกับก่อนรับชำระทุกสตางค์
- ถ้าบิลถูกยกไปแล้ว ยอดยกมาของบิลใหม่ถูกแช่แข็งไปแล้ว การคืนยอดจะทำให้สองใบไม่ตรงกัน

ถ้าบันทึกผิดหลายก้อน ให้ยกเลิกจากก้อนล่าสุดย้อนลงไป แล้วบันทึกใหม่

### GET /api/receipts/{id}/payments

ตอบ array ของการชำระรูปเดียวกับใน `payments` ของใบเสร็จ ใช้ตอนหน้าเว็บต้องการแค่ประวัติการชำระ

## หนี้ค้าง

### GET /api/debts

หนึ่งแถวต่อหนึ่งสัญญาที่ใบล่าสุดยังมี `balanceDue` มากกว่า 0 เรียงจากค้างนานสุด
ใบที่ถูกยกยอดไปแล้วไม่ถูกนับซ้ำ เพราะยอดของมันอยู่ในใบล่าสุดแล้ว

```json
[
  {
    "leaseId": 4,
    "roomNumber": "101",
    "tenantName": "มานี รักเรียน",
    "receiptId": 12,
    "receiptNo": "RC-2026-0012",
    "billingMonth": "2026-11",
    "balanceDue": 5145.00,
    "oldestUnpaidDueDate": "2026-12-05",
    "daysOverdue": 0,
    "bucket": "0-30"
  }
]
```

- `oldestUnpaidDueDate` ความหมายเดียวกับในใบเสร็จ ตามตัวอย่างใบตุลาคมถูกตัดครบแล้ว จึงเป็นของใบพฤศจิกายน
- `daysOverdue` คือจำนวนวันที่เลยวันนั้นมาแล้วตามเวลาไทย ยังไม่ถึงกำหนดเป็น 0
- `bucket` เป็น `0-30` (0 ถึง 30 วัน), `31-60` หรือ `61+`

## ยกยอดและดอกเบี้ย

### ตอนออกใบใหม่ (`POST /api/receipts`)

1. **ยอดยกมา** ใบก่อนหน้าทุกใบของสัญญาเดียวกันที่ยังมี `outstandingAmount` ถูกรวมเป็น `previousBalance` ของใบใหม่
   และ `carriedToReceiptId` ของใบเหล่านั้นเปลี่ยนมาชี้ใบใหม่ ใบที่เคยถูกยกไปบิลเดือนก่อนแต่ยังค้างอยู่ถูกยกต่อมาที่บิลนี้ ไม่นับซ้ำ
2. **ดอกเบี้ย** คิดจากต้นเงินคงเหลือของใบก่อนหน้าที่ **เลยกำหนดแล้ว ณ วันออกใบ (10 พ.ย.)**
   คือวันออกใบตามเวลาไทยเลย `dueDate + วันผ่อนผัน` ไปแล้ว คูณอัตราต่อเดือนที่สัญญาใบนั้นล็อกไว้ ปัดครึ่งขึ้นสองตำแหน่ง
   ดอกเบี้ยที่ค้างจากเดือนก่อนไม่ถูกเอามาคิดดอกเบี้ยอีก
   ใบที่ยังไม่ถึงกำหนดตอนออกใบใหม่จึงไม่ถูกคิดดอกเบี้ย ถ้าผู้เช่าจ่ายทันก่อนครบกำหนดก็ไม่เสียดอกเบี้ย
3. **ยอดรวม** = ค่าใช้จ่ายเดือนนี้ + ยอดยกมา + ดอกเบี้ย

ใบของสัญญาหนึ่งต้องออกตามลำดับเดือน ออกใบของเดือนที่เก่ากว่าใบล่าสุดที่มีอยู่แล้วได้ 409
เพราะยอดยกมาของใบที่ออกไปแล้วถูกแช่แข็งไว้ ใบที่แทรกเข้ามาทีหลังจะไม่ถูกนับในยอดเหล่านั้น
ใบของเดือนเดียวกันออกซ้ำไม่ได้อยู่แล้ว (409 เดิม)

ตัวอย่างค้างสามเดือนติด อัตรา 1.5% ไม่มีวันผ่อนผัน ทุกใบออกวันที่ 1 ของเดือนถัดไป (เลยกำหนดของใบก่อนหน้าแล้ว)

| ใบ | ค่าใช้จ่ายเดือนนี้ | ชำระแล้วก่อนออกใบถัดไป | ยอดยกมา | ต้นเงินที่คิดดอกเบี้ย | ดอกเบี้ย | ยอดรวม |
| --- | --- | --- | --- | --- | --- | --- |
| ต.ค. | 5,000.00 | 2,000.00 | 0.00 | - | 0.00 | 5,000.00 |
| พ.ย. | 5,100.00 | 0.00 | 3,000.00 | 3,000.00 | 45.00 | 8,145.00 |
| ธ.ค. | 5,000.00 | - | 8,145.00 | 8,100.00 | 121.50 | 13,266.50 |

ดอกเบี้ยของเดือนธันวาคมคิดจาก 3,000 + 5,100 = 8,100 ไม่ใช่ 8,145 เพราะ 45.00 เป็นดอกเบี้ย

### แก้ใบเสร็จ (`PUT /api/receipts/{id}`, SSK-155)

แก้ได้เฉพาะ **ใบล่าสุดของสัญญาที่ยังไม่มีการชำระบนบิลนี้และยังไม่ถูกตัดยอด**
- ใบที่ถูกยกยอดไปแล้ว ยอดของมันอยู่ในบิลใหม่แล้ว แก้แล้วสองใบจะไม่ตรงกัน
- ใบที่มีการชำระแล้ว ยอดที่ตัดไปจะไม่ตรงกับยอดใหม่
- แก้หน่วยน้ำไฟของใบล่าสุดได้ตามเดิม ยอดยกมากับดอกเบี้ยที่แช่แข็งไว้ไม่เปลี่ยน
- เดือนใหม่ต้องไม่เก่ากว่าใบก่อนหน้าของสัญญา

### PUT /api/apartment-config/late-interest

```json
{ "lateInterestPercentPerMonth": 1.5, "graceDays": 0 }
```

- ตอบรูปเดียวกับ `GET /api/apartment-config` ซึ่งจะมีสองฟิลด์นี้เพิ่ม
- `lateInterestPercentPerMonth` เป็น 0 ถึง 100 ปัดเหลือสองตำแหน่ง 0 คือไม่คิดดอกเบี้ย
- `graceDays` เป็นจำนวนเต็ม 0 ถึง 31
- **มีผลกับสัญญาที่ทำหลังจากนี้เท่านั้น** สัญญาใหม่คัดลอกสองค่านี้ไปตอนเซ็น
- `LeaseResponse` จะมี `lateInterestPercentPerMonth` กับ `graceDays` ของสัญญาใบนั้นเพิ่ม
- สัญญาที่ทำก่อน Phase 2 เป็น 0 ทั้งคู่ คือไม่คิดดอกเบี้ย ตามข้อสรุป SSK-164

## บัญชีรับเงินและ QR PromptPay

### PUT /api/apartment-config/bank-account

```json
{
  "bankName": "Kasikornbank",
  "accountName": "Sakura Soul Apartment",
  "accountNumber": "012-3-45678-9",
  "promptPayId": "0812345678"
}
```

- `bankName`, `accountName` และ `accountNumber` ต้องส่งมาครบทั้งสามช่อง หรือว่างทั้งสามช่อง (ว่างคือเลิกแสดงบัญชีบนใบใหม่)
- `accountNumber` เก็บตามที่กรอก ต้องมีตัวเลข 10 ถึง 15 หลัก คั่นด้วยขีดหรือเว้นวรรคได้
- `promptPayId` ไม่บังคับ แต่ใส่ได้เฉพาะเมื่อมีบัญชีครบสามช่องแล้ว
  ต้องเป็นเบอร์มือถือ 10 หลักที่ขึ้นต้นด้วย 0 หรือเลขประจำตัว 13 หลัก (มีขีดได้)
- **มีผลกับใบเสร็จที่ออกหลังจากนี้เท่านั้น** ใบเก่าแสดงบัญชีตามสำเนาของตัวเอง
- backend ไม่เขียนเลขบัญชีหรือ PromptPay ID ลง log เลย แม้แต่ตอนค่าผิด
- **ความเสี่ยงที่ยอมรับใน Phase 2 (10 พ.ย.)** ถ้าปิดบัญชีเดิม ใบล่าสุดที่ออกไปแล้วจะยังพาผู้เช่าไปโอนเข้าบัญชีเดิมจนกว่าจะออกใบถัดไป
  ไม่มีปุ่ม "ออกใบแจ้งหนี้ใหม่" ในเฟสนี้ แอดมินต้องแจ้งผู้เช่าเอง

### QR บนใบเสร็จ

- `promptPayPayload` เป็นข้อความ EMV ตามมาตรฐาน Thai QR Payment พร้อม CRC16
  - จำนวนเงินคือ **`balanceDue` ณ ตอนที่ขอข้อมูลหรือสร้างเอกสาร** รับชำระบางส่วนแล้ว QR จะเปลี่ยนเป็นยอดที่เหลือ
  - มีเฉพาะใบล่าสุดที่ `balanceDue` มากกว่า 0
- หน้าเว็บวาด QR จากข้อความนี้ได้เลยด้วยแพ็กเกจ `qrcode` ที่มีอยู่ ไม่ต้องสร้าง payload เอง
- **เลิกใช้รูป QR ที่อัปโหลดเอง** เพราะเป็นภาพนิ่งที่ใส่ยอดของแต่ละใบไม่ได้
- PDF และอีเมลของใบล่าสุดแสดง ยอดรวม / ชำระแล้ว / คงเหลือ (`totalAmount` / `paidAmount` / `balanceDue`) บล็อกบัญชีรับเงิน และ QR
  - ใบที่ถูกยกยอดแสดงบรรทัด "Carried to RC-…" แทนยอดคงเหลือ และไม่มี QR
  - ใบที่ไม่มีสำเนาบัญชีไม่แสดงบล็อกบัญชี ไม่ขึ้น error

ส่งได้สองแบบ แบบใดแบบหนึ่งเท่านั้น

```json
{ "receiptIds": [12, 13, 14] }
```

```json
{ "month": "2026-11", "status": "PENDING" }
```

- ใช้แม่แบบเดียวกับ `GET /api/receipts/{id}/pdf` ทุกอย่าง รวมบรรทัดค่าใช้จ่ายพิเศษและ QR (ขึ้นตามกฎของหัวข้อ QR)
- `status` ในแบบที่สองไม่บังคับ ไม่ส่งคือทุกสถานะ ใช้สถานะแบบเดียวกับ `status` ของใบเสร็จ

## รายงานสรุป

### GET /api/reports/summary

query: `groupBy=unit|tenant|month` (บังคับ), `from=YYYY-MM`, `to=YYYY-MM` (บังคับทั้งคู่ ช่วงไม่เกิน 10 ปี)
และตัวกรองไม่บังคับ `floor`, `roomId`, `tenantId`, `status` (สถานะแบบเดียวกับใบเสร็จ)

ตัวอย่างห้อง 101 ช่วงตุลาคมถึงพฤศจิกายน หลังรับชำระ 3,000.00 ตามเรื่องเดียวกับข้างบน

```json
{
  "groupBy": "unit",
  "from": "2026-10",
  "to": "2026-11",
  "rows": [
    {
      "key": "101",
      "label": "101",
      "receiptCount": 2,
      "rent": 7000.00,
      "electricUnits": 214.00,
      "electricAmount": 1712.00,
      "waterUnits": 16.00,
      "waterAmount": 288.00,
      "commonAreaFee": 600.00,
      "internetFee": 500.00,
      "extraCharges": 0.00,
      "lateInterest": 45.00,
      "billed": 10145.00,
      "received": 5000.00,
      "outstanding": 5145.00
    }
  ],
  "total": {
    "receiptCount": 2,
    "rent": 7000.00,
    "electricUnits": 214.00,
    "electricAmount": 1712.00,
    "waterUnits": 16.00,
    "waterAmount": 288.00,
    "commonAreaFee": 600.00,
    "internetFee": 500.00,
    "extraCharges": 0.00,
    "lateInterest": 45.00,
    "billed": 10145.00,
    "received": 5000.00,
    "outstanding": 5145.00
  }
}
```

- รวมจากใบเสร็จที่ `billingMonth` อยู่ในช่วง อ่านตัวเลขจากสำเนาในใบทั้งหมด ผู้เช่าที่ย้ายออกไปแล้วยังอยู่ในรายงาน
- `billed` = ค่าใช้จ่ายของเดือน + ดอกเบี้ย **ไม่รวมยอดยกมา** ไม่งั้นหนี้ก้อนเดียวถูกนับซ้ำทุกเดือนที่ถูกยก
- `received` คือผลรวม `settledAmount` ของใบเหล่านั้น คือเงินที่ถูกตัดเข้าใบของเดือนนั้นจริง
  **ไม่ใช่เงินที่รับเข้ามาในเดือนนั้น** ตามตัวอย่าง 3,000.00 ที่รับวันที่ 1 ธ.ค. นับเป็นของใบตุลาคม
- `outstanding` = `billed - received` ณ วันนี้ เท่ากับผลรวม `outstandingAmount` ของใบในช่วง
  ถ้าช่วงครอบทุกใบที่ยังค้าง ผลรวมจะเท่ากับหน้าหนี้ค้าง
- ผลรวมของแต่ละแบบการจัดกลุ่มในช่วงเดียวกันเท่ากันเสมอ
- `total` มีทุกช่องเหมือนแถวยกเว้น `key` กับ `label` ใช้ทำแถวรวมท้ายตาราง
- `key` ของ `groupBy=month` เป็น `YYYY-MM` ส่วน `label` เป็นข้อความโชว์ เช่น `Nov 2026`

### GET /api/reports/summary.csv

- query เดียวกัน ได้ไฟล์ `summary-unit-2026-10-2026-11.csv`
- UTF-8 มี BOM ให้ Excel เปิดภาษาไทยได้ ขึ้นบรรทัดแบบ CRLF ใส่ quote ตาม RFC 4180
- แถวแรกเป็นหัวคอลัมน์ภาษาอังกฤษ แถวสุดท้ายเป็นแถวรวม

- **รอบเตือนใบค้างรายเดือน (SSK-143)** ส่งเฉพาะใบล่าสุดของแต่ละสัญญาที่ `balanceDue` มากกว่า 0 หนึ่งฉบับต่อสัญญา
  ไม่ส่งใบที่ถูกยกยอดแล้ว และใบ `PARTIAL` ก็ถูกเตือนด้วย
- **metric ของ Grafana (SSK-184)** ยอดค้างรวมใช้ผลรวม `outstandingAmount` และใบเกินกำหนดนับจากใบล่าสุดที่ `overdue`
  รายได้ของเดือนนับจากการชำระที่ `paidOn` อยู่ในเดือนนั้น
- **การ์ดสรุปบนหน้า Payments** ถ้ารวมยอดเองให้ใช้ `outstandingAmount` หรือ `balanceDue` ของใบล่าสุด ห้ามรวม `totalAmount` ข้ามใบ เพราะนับยอดยกมาซ้ำ

## สิ่งที่หน้าเว็บต้องเปลี่ยน

ไฟล์ที่เกี่ยวข้องอยู่ใน `frontend/src/domain/paymentPhase2.ts`, `pages/PaymentsPage.tsx`, `dialogs/RecordPaymentDialog.tsx`,
`dialogs/BillingSettingsDialog.tsx`, `components/GenerateReceiptModal.tsx`, `dialogs/BulkPrintReceiptsDialog.tsx`,
`components/PaymentHistoryTab.tsx` และ `components/SummaryReportsTab.tsx`

**ตัวเลขที่หน้าเว็บคิดเองจาก localStorage ตอนนี้ใช้เทียบกับ backend ไม่ได้** ถ้าไม่ตรงกันให้ยึดตัวอย่างในเอกสารนี้
`computeInvoiceBalances` หักเงินที่รับออกจากยอดรวมตรง ๆ ไม่แยกดอกเบี้ยกับต้นเงิน และ `calculateInterest` คิดจากต้นเงินก้อนเดียว
หลังรับชำระบางส่วน ยอดคงเหลืออาจเท่ากัน แต่ดอกเบี้ยเดือนถัดไปจะต่าง เพราะ API ตัดดอกเบี้ยก่อนแล้วคิดดอกเบี้ยใหม่จากต้นเงินที่เหลือจริง

1. **รับชำระ**
   - ปุ่มรับชำระมีเฉพาะใบที่ `latest` เป็น `true` และ `balanceDue` มากกว่า 0 ไม่ใช่ทุกแถวที่มียอดค้าง
   - ทุกการชำระทั้งบางส่วนและเต็มจำนวนเรียก `POST /api/receipts/{id}/payments` แล้วโหลดรายการของสัญญาใหม่
   - เลิกเก็บการชำระใน `sakura_payment_records_v2` และเลิกสร้างแถวประวัติขึ้นมาเองสำหรับใบที่ไม่มีบันทึก
     (ตอนนี้ใส่ `'Bank transfer'` กับ `transfer-102.pdf` ให้ทุกใบ)
   - ตัวเลขตายตัวใน `PaymentHistoryTab` (`17645`, `'1 / 4'`, `"November 2026"`) ต้องอ่านจาก API
2. **ยกเลิกการชำระ** เพิ่มปุ่ม void ที่การชำระล่าสุดของสัญญา
3. **สถานะและยอด**
   - อ่าน `status`, `overdue`, `paidAmount`, `balanceDue` และ `outstandingAmount` จาก API
   - ลบการคิด `InvoiceBalances` ในหน้าเว็บทั้งหมด รวม `ROOM_CARRYOVERS` (101 = 2,000, 202 = 1,500) และสูตรดอกเบี้ยแบบคงที่
   - ยอดยกมาตอนนี้ผูกกับ **ห้อง** ผู้เช่าใหม่จึงรับหนี้ของคนเก่า และใบเก่าถูกยกซ้ำทุกเดือน ของจริงผูกกับ **สัญญา** และไม่นับซ้ำ
   - ใบที่มี `carriedToReceiptId` ให้โชว์ว่ายกไปบิลไหน ไม่ใช่โชว์เป็นยอดที่ต้องจ่ายอีกแถว
4. **ตั้งค่า**
   - ฟอร์มดอกเบี้ยส่ง `PUT /api/apartment-config/late-interest` และเพิ่มช่องวันผ่อนผัน
   - ฟอร์มบัญชีส่ง `PUT /api/apartment-config/bank-account`
   - ลบค่าตัวอย่างที่เติมให้เองตอนบันทึก (`'Kasikornbank'`, `'012-3-45678-9'`, `'0812345678'`) และช่องอัปโหลดรูป QR
5. **QR**
   - แสดงเมื่อ `promptPayPayload` ไม่เป็น `null` เท่านั้น ใบที่จ่ายครบแล้วตอนนี้ยังขึ้น QR อยู่
   - บัญชีบนใบอ่านจาก `bank` ของใบนั้น ไม่ใช่จากค่าตั้งปัจจุบัน
   - เลิกพิมพ์เลขบัญชีลง PDF ที่สร้างในเบราว์เซอร์
6. **พิมพ์รวม** ดาวน์โหลด PDF จาก `POST /api/receipts/print` แทน `window.print()` ของรายการการชำระ
7. **รายงาน** อ่านจาก `GET /api/reports/summary` และดาวน์โหลด CSV จาก `.csv`
   ลบ `INITIAL_REPORT_ROWS` และการรวมยอดในหน้าเว็บ ยอดค้างที่บวกข้ามเดือนตอนนี้ขัดกับข้อความบนหน้าจอเอง
8. **แก้ใบเสร็จ** ปุ่มแก้มีเฉพาะใบล่าสุดที่ยังไม่มีการชำระ

## ที่ยังไม่มีในเฟสนี้

- **ปุ่ม "ออกใบแจ้งหนี้ใหม่" เมื่อบัญชีเปลี่ยน** ดูความเสี่ยงในหัวข้อบัญชีรับเงิน
- **เงินเกินหรือเครดิตยกไปเดือนหน้า** รับเกินยอดไม่ได้ (400) ไม่มีการเก็บเงินเกินไว้หักบิลถัดไป
- **การเลือกเองว่าจะตัดใบไหน** ระบบตัดแบบ FIFO เสมอ
- **การแก้ไขการชำระ** ให้ยกเลิกแล้วบันทึกใหม่
- **ดอกเบี้ยรายวันหรือทบต้น** เป็นดอกเบี้ยแบบง่ายรายเดือนตามข้อสรุป SSK-164
- **ออกใบย้อนเดือนแทรกระหว่างใบที่มีอยู่** ต้องออกตามลำดับเดือน
