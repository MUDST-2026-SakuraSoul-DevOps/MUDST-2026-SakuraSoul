## อัตราต่อห้องตามช่วงเวลา (SSK-162, migration V17)

**สถานะ:** ทำแล้ว ตาราง `room_rate` (เพิ่มอย่างเดียว) endpoint สามตัวตามเอกสารหน้าเว็บ

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/rooms/{id}/rates` | ประวัติอัตราของห้อง ใหม่ก่อนเก่า ว่างได้ ห้องไม่มีได้ 404 |
| POST | `/api/rooms/{id}/rates` | เพิ่มอัตราใหม่ ตอบ 201 / 400 / 404 / 409 |
| GET | `/api/room-rates?from=YYYY-MM` | อัตราของทุกห้องที่เริ่มตั้งแต่เดือนนั้น เก่าก่อนใหม่ เดือนเดียวกันเรียงตามห้อง ไม่ส่ง `from` ได้ทั้งหมด |

**กฎ**
- อัตรา ณ เดือนหนึ่ง = แถวล่าสุดที่ `effectiveFrom <= เดือนนั้น` ถ้าไม่มีใช้ค่าตั้งต้นเดิม (ค่าเช่าตามชนิดห้อง + `apartment_config`)
  อยู่ที่ `RoomRateRepository.inEffect` ที่เดียว
- **สร้างสัญญา (`POST /api/leases`)** ถ้าห้องมีอัตราที่มีผลในเดือนของ `startDate` สัญญาใหม่ได้ **ค่าทั้งห้าตัว** จากอัตรานั้น
  (ค่าเช่า ค่าไฟ ค่าน้ำ ค่าส่วนกลาง ค่าอินเทอร์เน็ต) ค่าที่ส่งมาในคำขอถูกเมิน มีแค่เงินมัดจำที่ยังมาจากคำขอ
  ห้องที่ไม่มีอัตราเฉพาะทำแบบเดิมทุกอย่าง
- สัญญาที่ทำไปแล้วไม่เปลี่ยน แก้สัญญาก็คงค่าที่ล็อกไว้ (SSK-180)
- `baseRent` ของ `GET /api/rooms` และ `GET /api/rooms/{id}` คือค่าเช่าจากอัตราที่มีผล **เดือนนี้** ถ้าไม่มีใช้ค่าตามชนิดห้อง
  อัตราที่ตั้งไว้ล่วงหน้าของเดือนหน้ายังไม่มีผลกับตัวเลขนี้
- ลบห้อง (`DELETE /api/rooms/{id}`) หรือลดผังตึก อัตราของห้องนั้นถูกลบตามไปด้วย ไม่ได้ 409

**ลำดับการตรวจของ POST** ห้องไม่มี (404) → ค่าผิด (400) → ตั้งย้อนหลังทับเดือนที่ห้องนี้ออกบิลแล้ว (409) → มีอัตราเริ่มเดือนเดียวกันแล้ว (409)
ถ้าชนทั้งสองกฎพร้อมกันได้ข้อความย้อนหลัง เหมือน backend จำลอง

| สถานะ | เมื่อไหร่ | `detail` |
| --- | --- | --- |
| 400 | `effectiveFrom` ไม่ใช่ `YYYY-MM` | `Please choose the month the rate starts (YYYY-MM)` |
| 400 | ไม่ส่งค่าเช่า | `Monthly rent must be a number` |
| 400 | ค่าเช่าติดลบ | `Monthly rent cannot be negative` |
| 400 | ค่าเช่าเกิน 1,000,000 | `Monthly rent is too high` |
| 400 | อัตราสี่ตัวผิด | ข้อความเดียวกับ `PUT /api/apartment-config` เช่น `Electricity rate per unit is too high. The maximum is ฿1,000.00` |
| 400 | โน้ตยาวเกิน 200 ตัว | `The note must be 200 characters or fewer` |
| 400 | `from` ของ `GET /api/room-rates` ผิดรูปแบบ | `from must be YYYY-MM` |
| 404 | ไม่พบห้อง | `No unit with id 999` |
| 409 | ห้องนี้มีใบเสร็จของเดือนนั้นหรือหลังจากนั้นแล้ว | `A bill for 2026-11 or later has already been issued for this unit. Choose a later month.` |
| 409 | มีอัตราที่เริ่มเดือนเดียวกันแล้ว | `A rate starting 2026-12 already exists for this unit` |

**จุดที่ต่างจากเอกสารและ backend จำลองของหน้าเว็บ**
1. **อัตราของห้องชนะค่าในคำขอ (ทีมตัดสิน 10 พ.ย. 2569)** เอกสารหน้าเว็บบอกว่าคัดลอกเฉพาะช่องที่คำขอไม่ได้ส่งมา
   แต่ฟอร์ม Create Contract ส่งอัตราของ Apartment Config มาครบทุกครั้ง ถ้าทำตามเอกสาร อัตราน้ำไฟของห้องจะไม่เคยถูกใช้
   และเกณฑ์ตรวจในการ์ด (สัญญาใหม่ พ.ย. ได้ 8 ธ.ค. ได้ 9) จะไม่ผ่าน
   **หน้าเว็บควรแก้** ให้ฟอร์มโชว์ค่าของอัตราห้องที่มีผลในเดือนของ `startDate` แบบอ่านอย่างเดียว
   (ตอนนี้ฟอร์มโชว์ `baseRent` ของเดือนนี้ ซึ่งผิดถ้าเลือกวันเริ่มเป็นเดือนที่อัตราเปลี่ยน)
   และ backend จำลองควรทำแบบเดียวกัน
2. **โน้ตจำกัด 200 ตัว** ตามความยาวคอลัมน์ หน้าเว็บยังไม่ได้จำกัด
3. **`from` ที่ผิดรูปแบบได้ 400** backend จำลองเทียบเป็นข้อความเฉย ๆ
4. **ข้อความเพดานของอัตราเป็นบาทสองตำแหน่ง** (`฿1,000.00`) ตรงกับหน้าเว็บแล้ว เดิมฝั่ง Spring ยังตอบ `¥1,000` ตั้งแต่ก่อน SSK-126
   ข้อนี้แก้ที่ `PUT /api/apartment-config` ด้วย
5. **ลบห้องที่มีอัตรา** ลบได้และอัตราหายตามห้อง backend จำลองไม่ได้เช็คอัตราตอนลบห้องอยู่แล้ว จึงตรงกัน

**เทสที่คุม** `RoomRateRulesTest` (ตารางข้อความ), `LeaseServiceTest` (ค่าห้าตัวมาจากอัตราของเดือนเริ่มสัญญา และไม่อ่าน config),
`RoomServiceTest` (`baseRent`), `RoomRateApiTest` (ยิงถึง PostgreSQL จริง: ลำดับรายการ, สัญญา พ.ย./ธ.ค., 409 ย้อนหลังกับลำดับข้อความ,
400/404, `baseRent` ของเดือนนี้, ลดผังแล้วอัตราหาย, 401)

## ค่าใช้จ่ายพิเศษต่อห้อง (SSK-165, migration V18)

**สถานะ:** ทำแล้ว endpoint ห้าตัวตามเอกสารหน้าเว็บ ตารางสามชั้นตามทางเดินเดียวกับอัตรา
`room_extra_charge` (ค่าตั้งของห้อง) → คัดลอกตอนเซ็นไปที่ `lease_extra_charge` → คัดลอกตอนออกบิลไปที่ `receipt_line`

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/extra-charges` | รายการของทุกห้อง เรียงตามผังตึก (ชั้น แล้วเลขห้อง) แล้วตามลำดับที่เพิ่ม |
| GET | `/api/rooms/{id}/extra-charges` | รายการของห้องเดียว ตามลำดับที่เพิ่ม ห้องไม่มีได้ 404 |
| POST | `/api/rooms/{id}/extra-charges` | เพิ่ม ตอบ 201 / 400 / 404 |
| PUT | `/api/rooms/{id}/extra-charges/{chargeId}` | แก้ทั้งก้อน รวมถึงปิด/เปิด (`active`) ตอบ 200 / 400 / 404 |
| DELETE | `/api/rooms/{id}/extra-charges/{chargeId}` | ลบ ตอบ 204 / 404 / 409 |

```json
{ "id": 12, "roomId": 9, "label": "Parking space", "amount": 500.00,
  "recurrence": "MONTHLY", "startMonth": "2025-01", "endMonth": null, "active": true }
```

**กฎของรายการในห้อง**
- ชื่อตัดช่องว่างหัวท้าย ยอดเก็บสองตำแหน่ง `endMonth` ที่ว่างหรือ `null` คือไม่มีเดือนสุดท้าย
- `ONE_TIME` เก็บ `endMonth` เป็น `null` เสมอ แต่ยังตรวจรูปแบบก่อนทิ้งเหมือนหน้าเว็บ
- `active` ที่ไม่ส่งมา ตอน POST ถือเป็น `true` ตอน PUT **คงสถานะเดิม**
  กันการแก้ชื่อรายการที่ปิดไว้แล้วรายการกลับมาเก็บเงินเอง
- ลบได้เฉพาะรายการที่ยังไม่เคยเข้าสัญญาใบไหน ถ้าเคยแล้วให้ปิดแทน
- ลบห้องหรือลดผังตึก รายการของห้องนั้นถูกลบตามไปด้วย (ห้องที่เคยมีสัญญาลบไม่ได้อยู่แล้ว)

**ตอนสร้างสัญญา (`POST /api/leases`)** คัดลอกรายการที่ `active` ของห้องลง `LeaseResponse.extraCharges`
(`chargeId`, `label`, `amount`, `recurrence`, `startMonth`, `endMonth`, `active`)
- ชื่อ ยอด ความถี่ และช่วงเดือนล็อกตามวันเซ็น แก้รายการของห้องทีหลัง สัญญาเดิมไม่เปลี่ยน
- `active` คือสถานะ**ปัจจุบัน**ของรายการในห้อง ปิดที่ห้องแล้วทุกสัญญาที่มีสำเนาหยุดเก็บในบิลใหม่
- รายการที่ห้องได้เพิ่มทีหลังไม่คิดกับสัญญาเดิม เพราะ Phase 2 ไม่ทำ amendment
- ทุก response ของสัญญามี `extraCharges` เสมอ ไม่มีก็เป็น `[]`

**ตอนออกบิล (`POST /api/receipts`)** ต่อท้ายห้าบรรทัดมาตรฐานด้วยรายการในสัญญาที่ถึงรอบ ตามลำดับที่คัดลอก แล้วรวมเข้า `totalAmount`
- ปิดอยู่: ไม่เก็บ
- รายเดือน: เก็บเมื่อ `startMonth <= billingMonth <= endMonth` (ไม่มี `endMonth` คือไม่สิ้นสุด)
- ครั้งเดียว: เก็บเมื่อ `startMonth <= billingMonth` และยังไม่เคยอยู่ในบิลก่อนหน้าของสัญญาเดียวกัน
- บรรทัดเพิ่มเป็น `ReceiptItem` ปกติ ช่อง `chargeId` เป็นฟิลด์ใหม่ บรรทัดมาตรฐานส่ง `chargeId: null`

```json
{ "item": "Parking space", "detail": "Monthly", "usageValue": null, "usageUnit": null,
  "rate": null, "amount": 500.00, "chargeId": 12 }
```

- บิลเก็บสำเนาไว้ใน `receipt_line` แก้หรือปิดรายการทีหลัง บิลที่ออกไปแล้วไม่เปลี่ยน
- PDF ใบเสร็จ (และอีเมลที่แนบ PDF ตัวนั้น) แสดงบรรทัดเหล่านี้ด้วย
- แก้บิล (`PUT /api/receipts/{id}`) บรรทัดค่าใช้จ่ายพิเศษคงตามที่ออกไว้และยังรวมอยู่ในยอดใหม่
  เปลี่ยนเดือนที่เรียกเก็บก็ไม่คิดใหม่ว่าเดือนใหม่ถึงรอบรายการไหน เหมือน backend จำลอง
- สองบิลของสัญญาเดียวกันที่ออกพร้อมกันพอดี ค่าครั้งเดียวไม่ถูกเก็บซ้ำ unique index `receipt_line_one_time_uk` กันไว้
  ใบที่แพ้ถูกลองออกใหม่เองโดยไม่มีบรรทัดนั้น ผู้ใช้ไม่เห็น error

**ลำดับการตรวจ** ห้องไม่มี (404) → รายการไม่มีในห้องนี้ (404) → ค่าผิด (400) → ลบรายการที่อยู่ในสัญญาแล้ว (409)

| สถานะ | เมื่อไหร่ | `detail` |
| --- | --- | --- |
| 400 | ชื่อว่าง | `Please describe the charge` |
| 400 | ชื่อยาวเกิน 80 ตัว | `The description must be 80 characters or fewer` |
| 400 | ไม่ส่งยอด | `Amount must be a number` |
| 400 | ยอดติดลบ | `Amount cannot be negative` |
| 400 | ยอดเกิน 1,000,000 | `Amount is too high` |
| 400 | ความถี่ไม่ใช่ `ONE_TIME` หรือ `MONTHLY` | `Frequency must be ONE_TIME or MONTHLY` |
| 400 | เดือนแรกไม่ใช่ `YYYY-MM` | `Please choose the first month to charge (YYYY-MM)` |
| 400 | เดือนสุดท้ายไม่ใช่ `YYYY-MM` | `The last month must be YYYY-MM` |
| 400 | เดือนสุดท้ายมาก่อนเดือนแรก | `The last month cannot be before the first month` |
| 404 | ไม่พบห้อง | `No unit with id 999` |
| 404 | ไม่พบรายการในห้องนี้ | `No extra charge with id 12 for unit 109` |
| 409 | ลบรายการที่เคยเข้าสัญญาแล้ว | `"Parking space" is part of a contract or bill. Deactivate it instead.` |

**จุดที่ต่างจากเอกสารและ backend จำลองของหน้าเว็บ**
1. **PUT ที่ไม่ส่ง `active` คงสถานะเดิม** backend จำลองตั้งเป็นค่าว่าง หน้าเว็บส่ง `active` มาทุกครั้งอยู่แล้วจึงไม่กระทบ
2. **`active` ของสำเนาในสัญญาอ่านจากรายการในห้องทุกครั้งที่ตอบ** ไม่ได้เก็บแยก ผลเหมือน backend จำลองที่ไล่แก้สำเนาทุกครั้งที่ PUT
3. **ยอดที่ส่งเป็นข้อความ** ผ่านตัวอ่าน JSON กลางแบบ endpoint อื่น `"abc"` ได้ `The amount field must be a number`
   ส่วนสตริงตัวเลขอย่าง `"500"` รับได้ ยอดที่ไม่ส่งมาหรือเป็น `null` ได้ `Amount must be a number` ตามเอกสาร
   หน้าเว็บส่งยอดเป็นตัวเลขเสมอ จึงไม่กระทบ
4. **ไม่ส่งชื่อมาเลยได้ 400** `Please describe the charge` (backend จำลองพังที่ `.trim()`)
5. **ตัดช่องว่างหัวท้ายก่อนตรวจ** ทั้งชื่อและเดือน แบบเดียวกับ `billingMonth` ของใบเสร็จ (`Months`)
   `" 2026-12 "` จึงผ่าน และ `endMonth` ที่เป็นช่องว่างล้วนถือว่าไม่มีเดือนสุดท้าย หน้าเว็บตอบ `The last month must be YYYY-MM`
   ทั้งสองกรณี ส่วนชื่อใช้ `trim()` ของ Java ซึ่งไม่ตัดช่องว่างแบบ NBSP ที่ JavaScript ตัด
6. **ยอดปัดเป็นสองตำแหน่งตอนบันทึก** (`500.555` เป็น `500.56`) ตามคอลัมน์ `NUMERIC(10,2)` backend จำลองเก็บค่าดิบ
7. **ลำดับของ `GET /api/extra-charges`** ตามผังตึก (ชั้น แล้วเลขห้อง) backend จำลองเรียงเลขห้องแบบตัวเลข
   ผลเท่ากันเมื่อเลขห้องขึ้นต้นด้วยเลขชั้นแบบที่ผังตึกสร้าง
8. **PDF ใบเสร็จแสดงชื่อกับยอดของบรรทัด แต่ไม่แสดง `detail`** (`Monthly` / `One-time`) เพราะตารางในแม่แบบมีแค่
   รายการ หน่วย อัตรา และยอด ส่วน API ยังส่ง `detail` ให้หน้าเว็บตามปกติ

**ยังไม่ได้ทำ** เอกสารสัญญาเช่า (PDF) ยังไม่แสดงรายการค่าใช้จ่ายพิเศษที่ตกลงไว้ ถ้าทีมต้องการต้องทำแม่แบบเวอร์ชัน 2
(ดู `ContractTemplate`) สัญญาเก่าจะได้ยังพิมพ์ด้วยแม่แบบเดิม

**เทสที่คุม** `ExtraChargeRulesTest` (ตารางข้อความ), `LeaseExtraChargeTest` (กฎเดือนที่ถึงรอบ การคัดลอกเฉพาะที่เปิดอยู่),
`LeaseServiceTest` (สัญญาใหม่ได้สำเนา), `ReceiptServiceTest` (บรรทัดต่อท้าย ยอดรวม ค่าครั้งเดียว การลองใหม่เมื่อชน แก้บิลแล้วยอดไม่หาย),
`ExtraChargeApiTest` (ยิงถึง PostgreSQL จริง: CRUD และลำดับ, 400/404/401, สำเนาตอนเซ็นกับ 409 ตอนลบ, บิลสี่เดือนตามกฎทุกข้อ,
ย้ายเดือนของบิลไม่คิดบรรทัดใหม่, รายการใบเสร็จกับการส่งอีเมลโหลดบรรทัดได้, ค่าครั้งเดียวนับต่อสัญญาและ unique index ที่กันซ้ำ,
PDF มีบรรทัดและยอดรวม, ลบห้องหรือลดผังแล้วรายการหาย)

## นำเข้าค่าน้ำค่าไฟจาก CSV (SSK-166, migration V19)

**สถานะ:** ทำแล้ว ตาราง `meter_reading` หนึ่งแถวต่อห้องต่อเดือน endpoint สองตัวตามเอกสารหน้าเว็บ

| Method | Path | ทำอะไร |
| --- | --- | --- |
| POST | `/api/meter-readings/import?dryRun=true\|false&overwrite=true\|false` | multipart ช่อง `file` ตอบรายงาน 200 ทั้ง dry run และนำเข้าจริง ไฟล์ใช้ไม่ได้ทั้งไฟล์ได้ 400 |
| GET | `/api/meter-readings?month=YYYY-MM` | ค่าของเดือนนั้นเรียงตามผังตึก ไม่ส่ง `month` ได้ทุกเดือน ใหม่ก่อนเก่า |

ไม่ส่ง `dryRun` ถือเป็น `true` (ลืมส่งจึงไม่บันทึกอะไร) ไม่ส่ง `overwrite` ถือเป็น `false` เหมือน backend จำลอง
รูปร่างของรายงานกับ `MeterReading` ตรงกับเอกสารหน้าเว็บ `importedAt` เป็นเวลา UTC ถึงมิลลิวินาที เช่น `2026-11-10T09:15:00.123Z`

**กฎของไฟล์** ตามเอกสารหน้าเว็บทุกข้อ (หัวตาราง, UTF-8 มี BOM ได้, คั่นด้วยจุลภาค, ค่าในเครื่องหมายคำพูด, ข้ามบรรทัดว่าง, ตัดช่องว่างทุกช่อง)
อ่านด้วย commons-csv ผ่าน `common/csv/LineTrackedCsv`
- `line` นับหัวตารางเป็นบรรทัด 1 นับบรรทัดว่างและการขึ้นบรรทัดในเครื่องหมายคำพูดด้วย ตรงกับ `readCsv` ของหน้าเว็บ
- หน่วยเก็บสองตำแหน่งตามคอลัมน์ (`98.005` เป็น `98.01`) แบบเดียวกับหน่วยในใบเสร็จ
- `dryRun=false` บันทึกทุกแถวที่ถูกใน transaction เดียว แถวผิดไม่บันทึก แถวที่ห้องกับเดือนมีค่าแล้วข้าม เว้นแต่ `overwrite=true`
- `imported` คือแถวที่บันทึกจริง `skipped` คือแถวที่ถูกต้องแต่มีค่าเดิมและไม่ได้ขอให้ทับ (dry run นับว่าจะข้ามกี่แถว)
- สองการนำเข้าที่ทับห้องกับเดือนเดียวกันพร้อมกันไม่ได้ 409 ฐานข้อมูลตัดสินทีละแถวว่าข้ามหรือทับ (`INSERT ... ON CONFLICT`)
- ไม่แตะใบเสร็จที่ออกแล้ว ใบเสร็จเก็บหน่วยของตัวเอง

**ลำดับการตรวจ**
- ทั้งไฟล์ (400): ไม่มีไฟล์ → เกิน 1,000,000 ไบต์ → ไม่ใช่ UTF-8 → เครื่องหมายคำพูดไม่ปิด → หัวตาราง → ไม่มีแถวข้อมูล → เกิน 5,000 แถว
- รายแถว (อยู่ใน `errors` ปัญหาแรกของแถวเท่านั้น): จำนวนช่อง → ห้อง → รูปแบบเดือน → เดือนอนาคต → หน่วย → หน่วยเกินล้าน → ซ้ำในไฟล์

| ที่ไหน | เมื่อไหร่ | ข้อความ |
| --- | --- | --- |
| 400 | ไม่ส่งช่อง `file` | `Please choose a CSV file` |
| 400 | ไฟล์เกิน 1,000,000 ไบต์ | `The file is larger than 1 MB` |
| 400 | ไฟล์ไม่ใช่ UTF-8 | `The file must be UTF-8 text` |
| 400 | เครื่องหมายคำพูดไม่ปิดจนจบไฟล์ | `The file has a quote that is never closed. Check the file and try again.` |
| 400 | บรรทัดแรกไม่ใช่หัวตาราง (ไฟล์ว่างด้วย) | `The first line must be the header room_number,month,electric_units,water_units. Download the template to see the format.` |
| 400 | มีแต่หัวตาราง | `The file has no data rows.` |
| 400 | เกิน 5,000 แถว | `The file has more than 5,000 rows. Split it into smaller files.` |
| 400 | `month` ของ GET ผิดรูปแบบ | `month must be YYYY-MM` |
| 413 | ไฟล์เกิน 2 MB (เพดานของ Spring) | `The file is larger than 1 MB` |
| แถว | จำนวนช่องไม่ใช่ 4 | `Expected 4 columns but found 3` |
| แถว | ไม่มีห้องนี้ | `Unit 999 does not exist` หรือ `Unit (blank) does not exist` |
| แถว | เดือนผิดรูปแบบ | `Month "11/2026" must be YYYY-MM` |
| แถว | เดือนหลังเดือนนี้ | `Month 2099-01 is in the future` |
| แถว | หน่วยไม่ใช่ตัวเลขไม่ติดลบ | `Units must be numbers that are zero or more` |
| แถว | หน่วยเกิน 1,000,000 | `Units are too high` |
| แถว | ห้องกับเดือนซ้ำในไฟล์ (แถวหลัง) | `Unit 201 for 2026-11 appears more than once in the file` |

**ขนาดไฟล์ระหว่างทาง** nginx รับคำขอถึง 3 MB (`client_max_body_size 3m` ใน `location /api/`) Spring รับไฟล์ถึง 2 MB
ไฟล์ 1-2 MB จึงได้ 400 ข้อความข้างบน ไฟล์ 2-3 MB ได้ 413 ข้อความเดียวกัน ส่วนเกิน 3 MB ได้หน้า 413 ของ nginx
หน้าเว็บไม่ส่งไฟล์เกิน 1 MB อยู่แล้ว สองกรณีหลังจึงมาจากเครื่องมืออื่นเท่านั้น

**ค่ามิเตอร์เป็นประวัติของห้อง** (ทีมตัดสิน 10 พ.ย.) ห้องที่มีค่ามิเตอร์ลบไม่ได้
- `DELETE /api/rooms/{id}` ได้ 409 `Unit 101 has meter reading history and cannot be deleted`
- ลดผังตึกได้ 409 `Unit 110 has lease, maintenance or meter reading history and cannot be removed. Nothing was changed.`
  ข้อความนี้เปลี่ยนจากเดิม (`lease or maintenance history`) ให้ครอบเหตุผลใหม่
- ทั้งสองทางอ่านจาก `RoomHistorySource` ชุดเดียวกัน (สัญญา งานซ่อม ค่ามิเตอร์) ตารางประวัติใหม่เพิ่ม bean เดียวก็ถูกเช็คทั้งสองทาง

**จุดที่ต่างจากเอกสารและ backend จำลองของหน้าเว็บ**
1. **ไม่รับเดือนอนาคต** (ทีมตัดสิน 10 พ.ย.) เดือนปัจจุบันรับได้ หน้าเว็บยังไม่มีกฎนี้ dry run ของหน้าเว็บจึงอาจบอกว่าแถวนั้นถูก
2. **ไฟล์ต้องเป็น UTF-8** หน้าเว็บอ่านไฟล์ด้วย `file.text()` ซึ่งแทนไบต์ที่อ่านไม่ได้ด้วย `�` แล้วได้ error รายแถวที่อ่านไม่รู้เรื่อง
   (เช่นไฟล์ภาษาไทยที่ Excel เซฟเป็น ANSI/TIS-620) ฝั่งนี้ปฏิเสธทั้งไฟล์แทน
3. **หน่วยเกิน 1,000,000** ได้ `Units are too high` กันพิมพ์ผิดจนล้นคอลัมน์ หน้าเว็บไม่มีเพดาน
4. **ห้องที่มีค่ามิเตอร์ลบไม่ได้** backend จำลองยังลบได้ และข้อความลดผังเปลี่ยนตามข้อข้างบน
5. **`month` ของ GET ที่ผิดรูปแบบได้ 400** backend จำลองเทียบเป็นข้อความเฉย ๆ
6. **หน่วยเก็บสองตำแหน่ง** backend จำลองเก็บค่าดิบ
7. **เครื่องหมายคำพูดกลางค่า** (เช่น `ab"c`) เป็นตัวอักษรธรรมดาตาม RFC 4180 backend จำลองถือเป็นการเปิดเครื่องหมายคำพูด
   ไฟล์ที่โปรแกรมตารางเซฟไม่มีแบบนี้
8. **ไฟล์เกิน 2 MB ได้ 413** ข้อความเดียวกับ 400 ดูหัวข้อขนาดไฟล์
