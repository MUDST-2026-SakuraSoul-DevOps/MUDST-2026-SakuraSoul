# แผนงานฝั่ง frontend

บันทึกไว้ให้คนทำ frontend สองคนแบ่งงานกันได้โดยไม่ต้องมานั่งคุยใหม่ทุกรอบ
และให้คนที่มารับช่วงต่ออ่านแล้วรู้ว่าอะไรเสร็จแล้ว อะไรยังค้าง เพราะอะไร

อัปเดตล่าสุด 5 ก.ย. 2569

## สถานะตอนนี้

งานของ Natthanan เสร็จแล้วทั้ง 5 ใบ แยกเป็น 5 สาขาซ้อนกันเป็นชั้น
แต่ละสาขาต่อจากสาขาก่อนหน้า ไม่ได้แตกจาก `frontend` ทุกอัน เพราะทั้งห้า story
ใช้ชั้น API กองเดียวกัน ถ้าแตกจาก `frontend` ตรง ๆ สาขาหลังจะไม่มีไฟล์นั้นแล้ว build ไม่ผ่าน

ตอนเปิด PR ต้องเลือก base ให้ตรงกับสาขาก่อนหน้า ไม่ใช่ `frontend` ทุกอัน
มีแต่ PR แรกเท่านั้นที่ base เป็น `frontend` พอ PR แรก merge แล้ว GitHub จะเลื่อน base
ของ PR ถัดไปให้เอง merge เรียงตามลำดับในตาราง

**SSK-24 ยังต่อปุ่มเข้าหน้าจอไม่ได้** ตัวสร้างไฟล์กับปุ่ม `ExportLogButton` เสร็จและมีเทสครบ
ทั้งสาม scenario แล้ว แต่หน้า Maintenance Log ที่ story บอกให้วางปุ่มไว้เป็นของ SSK-19
ซึ่งอยู่ใน branch ของ papapymie ที่ยังไม่ merge ถ้าไปสร้างหน้านั้นเองจะกลายเป็น
`MaintenancePage.tsx` เวอร์ชันที่สามที่ชนกับอีกสองเวอร์ชัน

พอ SSK-19 merge เข้า `frontend` แล้ว การต่อปุ่มเหลือแค่สองบรรทัด

```tsx
import { ExportLogButton } from '../components/ExportLogButton'
// แล้ววางไว้ในหัวหน้า Maintenance Log โดยส่งรายการที่กรองแล้วเข้าไป
<ExportLogButton tickets={filteredTickets} />
```

ต้องส่งรายการ **ที่กรองแล้ว** เข้าไป ไม่ใช่ทั้งหมด เพราะ US-18-S2 ระบุว่าไฟล์ต้องมี
เฉพาะรายการที่ตรงกับตัวกรองที่ผู้ใช้เลือกไว้

**US-16-S3 เรื่อง snapshot อัตราในใบเสร็จ ทำที่ฝั่งนี้ไม่ได้** ใบเสร็จเป็นของ SSK-16
ข้อกำหนดคือใบเสร็จต้องเก็บอัตราที่ใช้ตอนออกใบไว้ในตัวมันเอง ห้ามอ้างกลับมาที่ตาราง config
ไม่งั้นพอแอดมินเปลี่ยนอัตรา ใบเสร็จเก่าทุกใบจะเปลี่ยนยอดตาม ซึ่งผิดทั้งทางบัญชีและกฎหมาย
เขียนไว้ใน `docs/api-contract-lease.md` ให้คนทำ SSK-16 แล้ว ส่วนฟอร์มตั้งอัตราบอกผู้ใช้
ไว้ชัดว่าอัตราใหม่มีผลกับใบเสร็จที่ออกหลังจากนี้เท่านั้น

ยังทำไม่ได้ในรอบนี้ ไม่ใช่เพราะลืม แต่เพราะต้องรอของอื่นก่อน

- **US-05-S2 race condition** ต้องพิสูจน์ด้วย integration test ฝั่ง backend ที่ยิงสองคำขอพร้อมกัน
  ฝั่งหน้าเว็บกับ backend จำลองเป็น single thread ทั้งคู่ ทดสอบข้อนี้แทนไม่ได้ อยู่ใน SSK-26
- **ต่อ backend จริง** ตาราง `lease` ยังไม่มี หน้าเว็บจึงรันบน backend จำลองอยู่
  ดูสัญญาที่ตกลงกันไว้ใน [api-contract-lease.md](api-contract-lease.md)

## แบ่งงานยังไงให้ไม่ชนกัน

กฎเดียวที่ต้องจำ **หนึ่งคนหนึ่งหน้า ต่อหนึ่งสาขา** ไฟล์ที่ใช้ร่วมกัน
(`src/components/`, `src/api/`, `src/domain/`) ถ้าจะแก้ให้บอกอีกคนก่อน
เพราะสองคนแก้ไฟล์เดียวกันคนละสาขาคือที่มาของ conflict เกือบทั้งหมดในโปรเจกต์ขนาดนี้

ถ้าต้องเพิ่ม component กลางจริง ๆ ให้แยกเป็น PR เล็ก ๆ ของตัวเองแล้ว merge ก่อน
ค่อยแตกสาขาหน้าจอออกมาจาก `frontend` ที่มีของนั้นแล้ว

## คิวงานถัดไป

เรียงตามที่ควรทำก่อนหลัง ตัวเลขในวงเล็บคือ Jira issue

### รอบก่อน 12 ก.ย.

1. **รีวิวและ merge ทั้ง 5 สาขาตามลำดับในตารางข้างบน**
   ต้องมีคนในทีมอย่างน้อยหนึ่งคน approve ตามกฎใน README และ CI ต้องเขียวทุกใบ
2. **ป็อปอัปเพิ่มผู้เช่า** (SSK-9 / US-03)
   ตอนนี้ฟอร์มเพิ่มผู้เช่าเป็นแผงที่กางออกมาใต้หัวข้อ ดีไซน์ใน Figma เป็นป็อปอัป
   (node 378:1960) เอา `src/components/Modal.tsx` ที่มีอยู่แล้วไปใช้ได้เลย งานไม่หนัก
3. **ป็อปอัปเพิ่ม/แก้ห้อง** (SSK-22 / US-16 บางส่วน)
   Figma มี Add Unit (node 378:2143) กับ Edit Unit (node 397:1344)
   ต้องรอ `POST` กับ `PUT /api/rooms` จากฝั่ง backend ก่อนจึงจะบันทึกได้จริง
   ถ้ายังไม่มี ให้ทำ UI กับเทสไว้ก่อนแล้วต่อ API ทีหลัง

### รอบก่อน 26 ก.ย.

4. **หน้า Login** (SSK-7, SSK-8 / US-01, US-02)
   ต้องรอ `SecurityConfig` ฝั่ง backend (SSK-28) ตกลงก่อนว่าจะใช้ session หรือ token
   เพราะสองแบบนี้ฝั่งหน้าเว็บเขียนไม่เหมือนกันเลย อย่าเพิ่งลงมือก่อนได้คำตอบ
5. **ต่อ backend จริงแทน backend จำลอง**
   พอ `V4__lease.sql` กับ endpoint ขึ้นแล้ว ตั้ง `VITE_API_MOCK=0` ใน `.env.development`
   แล้วรัน `npm run test` ถ้า `src/api/client.test.ts` ยังผ่าน แปลว่าสองฝั่งตรงกัน
   ถ้าไม่ผ่าน อ่าน diff แล้วคุยกับคนทำ backend ว่าใครหลุดจากสัญญา
6. **หน้า Payments** (SSK-16 / US-10) ต้องรอ endpoint ใบเสร็จจาก CR-04

### รอบก่อน 17 ต.ค.

7. **หน้า Maintenance** (SSK-18 ถึง SSK-21) ต้องรอ `V5__maintenance.sql` จาก CR-05
   หน้าเว็บมีที่รอไว้แล้วสองจุด ป็อปอัปห้องซ่อมบำรุงกับป้ายเตือนบนการ์ดห้อง
8. **หน้า Appliances** (SSK-23 / US-17)
9. **E2E ด้วย Playwright** (SSK-26) เริ่มจากเส้นทางเดียวก่อน
   เช็คอินห้องว่าง แล้วเช็คเอาต์ ผ่านหน้าเว็บจริง

## หน้าที่ยังเป็นโครงเปล่า รอเจ้าของ ticket มาทำต่อ

สามหน้านี้ยังใช้ค่าคงที่ที่ก๊อปมาจาก Figma ไม่ได้ต่อ API เพราะ endpoint ยังไม่มี
อย่าเผลอคิดว่าเป็นข้อมูลจริงตอนเดโม

| ไฟล์ | เป็นของ ticket |
| --- | --- |
| `src/pages/PaymentsPage.tsx` | SSK-16 ออกใบเสร็จ |
| `src/pages/MaintenancePage.tsx` | SSK-18 ถึง SSK-21 งานซ่อมบำรุง |
| `src/pages/AppliancesPage.tsx` | SSK-23 คลังอุปกรณ์ |

สามหน้านี้ติดมากับสาขาแรกเพราะเมนู sidebar ในดีไซน์มีเจ็ดเมนู ถ้าไม่มีไฟล์พวกนี้
router จะพังทั้งแอปจนเปิดหน้า Dashboard ไม่ได้ ไม่ได้ตั้งใจไปทำงานของคนอื่น
เจ้าของ ticket เขียนทับไฟล์ของตัวเองได้เลย ไม่ต้องเกรงใจ

## เช็คก่อนเปิด PR ทุกครั้ง

```bash
cd frontend
npm run lint
npm run test
npm run build
```

สามคำสั่งนี้คือสิ่งเดียวกับที่ `ci.yml` รันบน GitHub ถ้าผ่านที่เครื่องแล้วยังแดงบน CI
ให้สงสัยเรื่องเวอร์ชัน Node ก่อนเป็นอย่างแรก

## เขียนเทสยังไงให้ตรงกับที่วิชาต้องการ

Task ของวิชาเขียนไว้ว่า code review เป็น optional แต่ test ไม่ใช่
เทสที่มีอยู่ตอนนี้แบ่งเป็นสามชั้น ก๊อปรูปแบบไปใช้ต่อได้เลย

| ชั้น | ตัวอย่าง | เทสอะไร |
| --- | --- | --- |
| ตรรกะล้วน | `src/domain/lease.test.ts` | กฎช่วงวันที่ทับกัน ไม่แตะ DOM ไม่แตะ network |
| สัญญา API | `src/api/client.test.ts` | รูปร่าง payload รหัสสถานะ ข้อความ error |
| หน้าจอ | `src/pages/DashboardPage.test.tsx` | ผู้ใช้กดแล้วเห็นอะไร ยิงผ่าน backend จำลองจริง |

ตั้งชื่อเทสเป็นภาษาไทยที่อ่านแล้วรู้ว่าพังเรื่องอะไร และอ้าง user story ไว้ในคอมเมนต์หัวไฟล์
เวลาอาจารย์เปิดดูจะได้ตามได้ว่าเทสตัวไหนคุม acceptance criteria ข้อไหน
