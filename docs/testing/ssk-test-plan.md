# แนวทางทดสอบตาม User Story (SSK)

## E2E Testing

การทดสอบ E2E ใช้ Cypress (ตามที่อาจารย์กำหนด SSK-158) จำลองพฤติกรรมของผู้ใช้ผ่าน UI และครอบคลุมเส้นทางสำคัญตั้งแต่หน้าเว็บไปยัง API และฐานข้อมูลเมื่อเป็นชุด `live-api` รายละเอียดของแต่ละเคสใช้รูปแบบ `ID`, `Title`, `Preconditions`, `Steps`, `Input Data` และ `Expected Result` ตาม [E2E Test Case Catalogue](./e2e-test-cases.md)

| E2E project | API destination | Scope | Execution |
| --- | --- | --- | --- |
| `mock-api` | `src/api/mockApi.ts` | ตรวจ UI flow และผลลัพธ์บนหน้าเว็บโดยไม่แตะ Backend | CI ทุก PR |
| `stubbed-api` | Cypress `cy.intercept` | ตรวจการตอบกลับของ API ในกรณีที่ต้องควบคุม response | CI ทุก PR |
| `live-api` | Spring Boot + PostgreSQL จริง | ตรวจ UI → API → Database และพฤติกรรมที่ mock อาจมองไม่เห็น | CI ทุก PR (job `e2e-live` ยก stack ด้วย docker compose) |

ปัจจุบันมี E2E Test Case ทั้งหมด 36 เคส แบ่งเป็น 17 เคสที่ใช้ Mock/Stubbed และ 19 เคสที่ใช้ Live API จึงต้องรายงานผลแยกกัน ไม่รวมเป็นตัวเลขเดียวที่อาจทำให้เข้าใจว่าทุกเคสแตะ Backend จริง

การรายงาน E2E ต้องระบุ project ที่รัน, จำนวน passed/failed, ระยะเวลา, browser และ environment หากล้มเหลวให้ดูรายงาน HTML ที่ `e2e/cypress/reports/<project>/index.html` ซึ่งฝังรูปหน้าจอของเคสที่พังไว้ (รูปไฟล์แยกอยู่ที่ `e2e/cypress/screenshots/`) ใน CI คือ artifact `e2e-report` และ `e2e-live-report` เพื่อใช้วิเคราะห์ปัญหา

การตรวจด้วยมือใช้สำหรับ manual smoke demo ของเส้นทางสำคัญ เช่น Login → เพิ่มผู้เช่า → สร้างสัญญา → ตรวจ Dashboard → ออกบิล → Mark as Paid → Download PDF → Logout ไม่ใช่การทดแทน Automated E2E ทุกเคส

เอกสารนี้เป็นข้อตกลงร่วมกันว่า **ต้องพิสูจน์พฤติกรรมใด** ไม่ใช่รายการไฟล์เทสต์หรือรายงานว่าเทสต์ใดทำเสร็จแล้ว แหล่งที่มาของพฤติกรรมคือ [User Story ใน Jira](https://wishza2549.atlassian.net/issues/?jql=project%20%3D%20SSK%20AND%20issuetype%20%3D%20Story) และข้อตกลง API ใน `docs/` หากข้อกำหนดเปลี่ยน ให้แก้ User Story/ข้อตกลงที่เกี่ยวข้องก่อน แล้วจึงปรับเทสต์ตามพฤติกรรมที่ตกลงกัน

## วิธีใช้แผนนี้

1. เลือก scenario จากรหัส US/SSK ด้านล่าง แล้วเขียนเคสแบบ **Given–When–Then**: มีข้อมูล/สถานะอะไร → ผู้ใช้หรือระบบทำอะไร → ผลลัพธ์ที่สังเกตได้คืออะไร ภายในเทสต์สามารถจัดเป็น Arrange–Act–Assert ได้เหมือนกัน
2. ทดสอบในระดับที่พิสูจน์พฤติกรรมนั้นได้จริง ไม่จำเป็นต้องทำซ้ำทุกระดับ: กฎคำนวณใช้ unit test; การกรอก/คลิก/ข้อความบนจอใช้ frontend interaction test; การบันทึก ข้อผิดพลาด และข้อจำกัดข้อมูลใช้ backend/API integration test; เส้นทางสำคัญข้ามระบบใช้ E2E
3. ถ้าจำลอง API ใน frontend ให้จำลองเฉพาะขอบเขตการเชื่อมต่อ แล้วตรวจผลที่ผู้ใช้เห็นหรือคำขอที่ส่งจริง อย่าจำลองฟังก์ชันที่กำลังทดสอบจนเทสต์ผ่านทั้งที่พฤติกรรมจริงผิด
4. สำหรับข้อมูลผิด ให้ตรวจทั้งการปฏิเสธ/ข้อความแจ้งเตือนและการที่ข้อมูลเดิม **ไม่เปลี่ยน**; สำหรับข้อมูลถูก ให้ตรวจผลหลังบันทึกหรือโหลดใหม่ ไม่ดูเพียงว่าปุ่มถูกกด
5. กรณีที่ต้องอาศัยฐานข้อมูลจริง ความพร้อมกันของคำขอ หรือการสร้าง PDF ให้ทดสอบในระดับ backend/integration ด้วย; frontend interaction test อย่างเดียวพิสูจน์เรื่องเหล่านี้ไม่ได้

### Phase 2

ข้อกำหนด Phase 2 กำหนดพฤติกรรมเพิ่มอีก 13 ข้อและ bonus 4 ข้อ แถวด้านล่างแปลงข้อกำหนดเหล่านั้นเป็น scenario ที่ต้องพิสูจน์ ด้วยหลักเดียวกับตารางข้างบน รหัส `PH2-xx` กับเลข SSK ตรงกับการ์ดใน Jira ภายใต้ Epic [SSK-159](https://wishza2549.atlassian.net/browse/SSK-159) (Sprint SSA Sprint 2)

ตัวเลขและกฎที่ใช้ในเคสด้านล่างมาจากรายละเอียดในการ์ดของแต่ละข้อ ไม่ใช่ข้อเสนอของเอกสารนี้ เมื่อการ์ดแก้กฎ ให้แก้แถวนี้ตาม ไม่ใช่ทางกลับกัน

สองอย่างที่ตรวจกับโค้ดปัจจุบันแล้วและจะทำให้เคสของ PH2-02 ล้มตั้งแต่ยังไม่เริ่ม `frontend/nginx.conf` ไม่ได้ตั้ง `client_max_body_size` ไว้เลย จึงใช้ค่าตั้งต้นของ nginx ที่ 1 MB และ `application*.yml` ไม่ได้ตั้งขีดจำกัด multipart ของ Spring ไว้เช่นกัน เคส S5 ที่ขอไฟล์ 4 MB จะได้ 413 ตั้งแต่ชั้น proxy ก่อนถึง backend ถ้าไม่แก้ทั้งสองที่ก่อน

`UploadContractDialog.tsx` ที่หน้า Contracts เรียกใช้อยู่ **ยังไม่ต่อ backend** `handleUpload` เป็น `setTimeout` 500 ms แล้วปิดไดอะล็อก ไม่มีคำขอออกเครือข่าย และ state ตั้งต้นใส่ชื่อไฟล์ `CT-0042-signed.pdf` ไว้ล่วงหน้า ทำให้เปิดไดอะล็อกแล้วเห็นเหมือนมีไฟล์แนบอยู่แล้วทั้งที่ยังไม่มี ประเด็นนี้ต้องแจ้งเป็นข้อบกพร่องแยก ไม่ใช่ถือว่าเป็นงานที่ทำไปแล้วของ PH2-13

## ความหมายของข้อมูลสำคัญในการเตรียมเคส

ตารางนี้อธิบายว่าแต่ละค่าหมายถึงอะไรและควรใช้พิสูจน์อะไร ส่วนตัวเลขในหัวข้อถัดไปเป็น **ข้อเสนอให้ทีมพิจารณา** ไม่ใช่กฎที่ระบบบังคับใช้อยู่แล้ว และตัวเลขในข้อมูลตัวอย่างของเทสต์ไม่ใช่กฎธุรกิจ

### ค่าตั้งต้นที่เสนอให้ทีมยืนยันร่วมกัน

**สถานะโค้ดปัจจุบันก่อนปรับข้อกำหนด:** `electricRatePerUnit`/`waterRatePerUnit` รับ `0–1,000`; `commonAreaFee`/`internetFee` รับ `0–100,000` ทั้ง frontend และ backend และไม่รับค่าว่าง ค่าเช่าของสัญญาใหม่มาจากชนิดห้อง `SINGLE = 3,500`, `DOUBLE = 4,500` บาท ไม่ได้ใช้ `monthlyRent` ที่ส่งมาในคำขอ งานซ่อมรับ `cost = null` หรือ `0` ได้และไม่มีเพดานธุรกิจเฉพาะ (คอลัมน์ฐานข้อมูลเป็น `NUMERIC(10,2)`) ส่วน `stock`/`minStock` ต้องเป็นจำนวนเต็มไม่ติดลบ และการเติมของ `quantity` ต้องเป็นจำนวนเต็มมากกว่า `0` แต่ backend ยังไม่มีเพดานสต็อกต่อชนิด ฝั่ง frontend มี `maxStock` สำหรับตรวจสต็อก/จำนวนเติม ซึ่งยังไม่ใช่ฟิลด์ใน API จริง

ค่าด้านล่างเป็น **ข้อเสนอให้ทีมยืนยัน** ไม่ใช่ expected result ของเทสต์หรือกฎที่โค้ดบังคับใช้ทั้งหมด การปฏิเสธค่าติดลบเป็นกฎที่มีอยู่แล้ว แต่กฎอัตราน้ำไฟ `> 0`, เพดานค่ารายเดือนที่ต่ำลง และการจำกัดทศนิยมบางข้อยังต่างจากระบบปัจจุบัน โดยเฉพาะค่ารายเดือน: ถ้ามีการเรียกเก็บในเดือนนั้น ค่าเช่า/ค่าส่วนกลาง/อินเทอร์เน็ตไม่ควรเป็น `0` หรือว่าง; หากไม่เรียกเก็บจริงควรมีสถานะหรือกติกาแยก ไม่ใช้ `0` แทนโดยไม่มีคำอธิบาย จำนวนทศนิยมในตารางหมายถึงค่าที่ต้องการ **เก็บ/แสดง**; backend ปัจจุบันรับฟิลด์ที่เป็นทศนิยมเกิน 2 ตำแหน่งแล้วปัด ไม่ได้ปฏิเสธตั้งแต่รับข้อมูล

(ก) **กฎที่เสนอให้บังคับ:** อัตราต้องเป็นตัวเลขมากกว่า `0`; ไม่กำหนดขั้นต่ำ/ขั้นสูงเป็นตัวเลขคงที่ เพราะต้องตรวจอัตราที่เรียกเก็บและวิธีคำนวณจากบิลจริง **ช่วงที่เสนอให้เตือนเพื่อตรวจซ้ำ ไม่ใช่ปฏิเสธอัตโนมัติ:** ค่าไฟต่ำกว่า `2` หรือสูงกว่า `6` บาท/หน่วย; ค่าน้ำต่ำกว่า `8` หรือสูงกว่า `20` บาท/หน่วย ค่าเริ่มต้นในโค้ด `8` และ `18` เป็นข้อมูลตัวอย่าง ไม่ใช่หลักฐานว่าเรียกเก็บได้ตามกฎ [สคบ. ระบุว่าค่าน้ำและค่าไฟของธุรกิจให้เช่าที่อยู่อาศัยต้องไม่เกินอัตราที่ผู้ให้บริการเรียกเก็บจากผู้ประกอบธุรกิจ](https://www.ocpb.go.th/news_view.php?nid=18149) ระบบปัจจุบันคิด `หน่วยที่ใช้ × อัตราคงที่` ยังไม่ใช่[อัตราก้าวหน้าตามตัวอย่างของ กฟภ.](https://www.pea.co.th/news/corporate-news/2412) จึงต้องตกลงวิธีคำนวณก่อนเขียน expected result ของบิลแบบขั้นบันได ทั้งการตรวจเทียบบิลและการเตือนตามช่วงยังไม่มีในโค้ดปัจจุบัน

(ข) สต็อกเป็นของ **คลังส่วนกลางทั้งตึก แยกตามชนิดอุปกรณ์** ไม่ใช่จำนวนต่อห้องหรือผลรวมทุกชนิด `stock = 0` หมายถึงของหมดจริง ส่วน `minStock = 0` ทำให้เงื่อนไข `stock < minStock` ไม่เป็นจริง จึงไม่ขึ้น `LOW_STOCK` แม้ของหมด; หากต้องการเตือน ควรตั้ง `minStock > 0` ตัวอย่าง frontend ปัจจุบันตั้ง `maxStock` แยกเป็นหลอดไฟ `200`, ไส้กรองแอร์ `60`, ข้อต่อท่อ `120` ชิ้น ตัวเลขเหล่านี้เป็นเพียงข้อมูลตัวอย่าง ไม่ใช่เพดานทุกชนิด Frontend ตรวจ `stock`, `minStock`, `quantity` เทียบกับ `maxStock` ของชนิดนั้น แต่ backend ยังไม่มีฟิลด์/กฎ `maxStock` จึงยังไม่ใช่พฤติกรรมข้ามระบบ

หากอยากรับค่าผิดปกติแต่ยังอยู่ในเพดาน ให้เตือนเพื่อทวนก่อนบันทึกแทนการปฏิเสธทันที: ค่าส่วนกลาง `> 1,500` บาท/เดือน, อินเทอร์เน็ต `> 1,500` บาท/เดือน, ค่าเช่า `> 15,000` บาท/เดือน (กรณีเพิ่มชนิดห้องในอนาคต), ค่าซ่อม `> 100,000` บาท/งาน, ไฟ `> 1,000` หน่วย/ห้อง/รอบบิล หรือน้ำ `> 100` หน่วย/ห้อง/รอบบิล ตัวเลขเตือนเหล่านี้ก็เป็นข้อเสนอ ไม่ใช่กฎของโค้ดปัจจุบัน

| หัวข้อ/ตัวแปร | ความหมายภาษาไทย | ค่าจากโค้ดปัจจุบัน / ข้อเสนอ |
| --- | --- | --- |
| การปัดเศษเงิน (ข้อตกลงร่วม ไม่ใช่ฟิลด์ API) | วิธีปัดเศษเมื่อคำนวณยอดเงินและส่งค่าระหว่าง frontend/backend | backend ปัด `HALF_UP` เหลือ 2 ตำแหน่ง; เสนอให้ frontend แสดงผลตรงกันหลังเปลี่ยนเป็นบาท |
| `stock` เทียบกับ `minStock` | เกณฑ์ Low Stock | ใช้กฎเดิม: `stock < minStock` คือ `LOW_STOCK`; เท่ากันคือ `IN_STOCK` |
| `room.status` ก่อนซ่อมเป็น `AVAILABLE` | หลังปลดสถานะ `MAINTENANCE` โดยไม่มีสัญญาที่มีผลวันนี้ | `AVAILABLE` ตามโค้ดปัจจุบัน |
| `room.status` ก่อนซ่อมเป็น `OCCUPIED` | หลังปลดสถานะ `MAINTENANCE` ขณะสัญญายังมีผล | `OCCUPIED` ตามโค้ดปัจจุบัน |
| ฟอร์แมตไฟล์ส่งออก (ยังไม่มีฟิลด์เลือกฟอร์แมตใน API) | ประเภทไฟล์ที่ต้องรองรับใน US-18 | ปัจจุบัน `CSV` เท่านั้น; ฟอร์แมตอื่นต้องตกลงเพิ่ม |
| ตัวเลือกฟอร์แมตบนหน้าจอ | ต้องให้ผู้ใช้เลือกประเภทไฟล์ก่อนส่งออกหรือไม่ | ปัจจุบันไม่ต้องเลือกเพราะมีเพียง `CSV`; หาก User Story ต้องการหลายฟอร์แมตให้ตกลงเพิ่ม |

เมื่อทีมยืนยันข้อใดแล้ว ให้บันทึกค่าหรือกฎไว้ใน User Story/ข้อตกลง API ที่เป็นต้นทางก่อน จากนั้นจึงเพิ่มเคสขอบเขต เช่น ค่าต่ำสุด/สูงสุด ค่าพอดีขอบ ค่าที่เลยขอบ ค่าว่าง และค่าที่ต้องเตือนในเทสต์ที่เกี่ยวข้อง หากข้อเสนอต่างจากพฤติกรรมระบบปัจจุบัน ให้ทีมยืนยันการเปลี่ยน requirement ก่อนแก้โค้ดหรือเทสต์
