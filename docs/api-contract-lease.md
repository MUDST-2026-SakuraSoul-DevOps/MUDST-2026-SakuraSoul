# สัญญา API ของสัญญาเช่า (lease)

เอกสารนี้คือข้อตกลงระหว่างฝั่งหน้าเว็บกับฝั่ง Spring Boot ว่า endpoint ของสัญญาเช่าจะหน้าตาเป็นแบบไหน
ฝั่งหน้าเว็บเขียนตามนี้ไปแล้วและรันด้วย backend จำลองอยู่ (`frontend/src/api/mockApi.ts`)
เมื่อฝั่ง backend ทำตามนี้เสร็จ ให้ตั้ง `VITE_API_MOCK=0` ใน `frontend/.env.development`
แล้วหน้าเว็บจะต่อของจริงได้โดยไม่ต้องแก้โค้ดสักบรรทัด

ที่ต้องมีเอกสารนี้เพราะ US-05 ถึง US-09 ทั้งหมดหมุนรอบตาราง `lease` ที่ยังไม่มี
ถ้ารอให้ backend เสร็จก่อนค่อยเริ่มหน้าจอ จะเสียเวลาไปทั้งสปรินต์โดยไม่จำเป็น

เทสที่บังคับสัญญานี้อยู่ที่ `frontend/src/api/client.test.ts` อ่านไฟล์นั้นควบคู่กัน
ถ้า backend ตอบไม่เหมือนที่เขียนไว้ที่นี่ แปลว่ามีฝั่งใดฝั่งหนึ่งหลุดจากที่ตกลงกัน

## ตารางที่ต้องเพิ่ม

`V3__lease.sql`

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE lease (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id       BIGINT       NOT NULL REFERENCES room (id),
    tenant_id     BIGINT       NOT NULL REFERENCES tenant (id),
    start_date    DATE         NOT NULL,
    end_date      DATE,
    monthly_rent  NUMERIC(10, 2) NOT NULL,
    billing_cycle VARCHAR(10)  NOT NULL,
    status        VARCHAR(10)  NOT NULL,

    CONSTRAINT lease_rent_ck   CHECK (monthly_rent >= 0),
    CONSTRAINT lease_range_ck  CHECK (end_date IS NULL OR end_date >= start_date),
    CONSTRAINT lease_cycle_ck  CHECK (billing_cycle IN ('MONTHLY', 'YEARLY')),
    CONSTRAINT lease_status_ck CHECK (status IN ('ACTIVE', 'ENDED')),

    CONSTRAINT lease_no_overlap EXCLUDE USING gist (
        room_id WITH =,
        daterange(start_date, end_date, '[]') WITH &&
    ) WHERE (status = 'ACTIVE')
);
```

สามเรื่องที่ห้ามพลาด

- ต้องมี `btree_gist` ก่อน ไม่งั้นเอา `room_id` ที่เทียบด้วย `=` มารวมใน exclusion constraint ไม่ได้
- ช่วงวันที่เป็นแบบปิดสองด้าน `'[]'` แปลว่าสัญญาเก่าจบวันที่ 31 ส.ค. กับสัญญาใหม่เริ่มวันที่ 31 ส.ค. ถือว่าทับกัน
  ฝั่งหน้าเว็บใช้กฎเดียวกันใน `frontend/src/domain/lease.ts` ถ้าจะเปลี่ยนเป็น `'[)'` ต้องเปลี่ยนพร้อมกันทั้งสองที่
- `WHERE (status = 'ACTIVE')` ทำให้สัญญาที่ปิดไปแล้วไม่กันห้องอีก ซึ่งเป็นพฤติกรรมที่ US-06-S1 ต้องการ

## Endpoint

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/leases` | รายการสัญญา รับ query `status`, `roomId`, `tenantId` |
| POST | `/api/leases` | สร้างสัญญา ตอบ 201 |
| PUT | `/api/leases/{id}` | แก้สัญญาทั้งก้อน |
| POST | `/api/leases/{id}/terminate` | ปิดสัญญา body `{ "endDate": "2026-09-30" }` |
| GET | `/api/rooms/{id}/maintenance` | ใบแจ้งซ่อมของห้อง (ของ epic CR-05 หน้าเว็บทนได้ถ้ายังไม่มี ตอบ 404 แล้วจะถือว่าไม่มีรายการ) |

`GET /api/rooms` เดิมต้องเพิ่มสามฟิลด์ ห้ามตัดฟิลด์เก่าทิ้ง

```json
{
  "id": 2,
  "roomNumber": "102",
  "floor": 1,
  "baseRent": 3500.00,
  "status": "OCCUPIED",
  "currentLease": {
    "id": 1,
    "tenantId": 1,
    "tenantName": "ยูกิ ทานากะ",
    "startDate": "2025-10-20",
    "endDate": "2026-09-16",
    "monthlyRent": 3500.00,
    "billingCycle": "MONTHLY"
  },
  "openMaintenanceCount": 0
}
```

- `status` เป็น `AVAILABLE` / `OCCUPIED` / `MAINTENANCE`
  ห้องที่ปิดซ่อมให้ตอบ `MAINTENANCE` เสมอ ถึงจะมีสัญญาค้างอยู่ก็ตาม
- `currentLease` เป็น `null` เมื่อไม่มีสัญญาที่ครอบวันนี้
- `openMaintenanceCount` คือจำนวนใบแจ้งซ่อมที่ยังไม่ปิด เอาไปติดป้ายบนการ์ดห้อง

`lease` ที่ตอบกลับจาก endpoint ของสัญญา

```json
{
  "id": 1,
  "roomId": 2,
  "roomNumber": "102",
  "tenantId": 1,
  "tenantName": "ยูกิ ทานากะ",
  "startDate": "2025-10-20",
  "endDate": "2026-09-16",
  "monthlyRent": 3500.00,
  "billingCycle": "MONTHLY",
  "status": "ACTIVE"
}
```

body ของ POST และ PUT

```json
{
  "roomId": 2,
  "tenantId": 1,
  "startDate": "2026-10-01",
  "endDate": null,
  "monthlyRent": 3500.00,
  "billingCycle": "MONTHLY"
}
```

`endDate` เป็น `null` ได้ แปลว่ายังไม่กำหนดวันจบ

## รหัสสถานะและข้อความ error

ทุก error ตอบเป็น `ProblemDetail` ตาม RFC 9457 เหมือนที่โปรเจกต์ทำอยู่แล้ว
ข้อความที่เอาไปโชว์ผู้ใช้อยู่ในฟิลด์ `detail`

| สถานะ | เมื่อไหร่ | `detail` ต้องมีอะไร |
| --- | --- | --- |
| 400 | `endDate` มาก่อน `startDate` | บอกว่าวันสิ้นสุดต้องไม่มาก่อนวันเริ่ม |
| 404 | ไม่พบห้องหรือผู้เช่าตาม id ที่ส่งมา | บอกว่าไม่พบอะไร id ไหน |
| 409 | ช่วงวันที่ทับกับสัญญา `ACTIVE` อื่นของห้องเดียวกัน | **เลขห้อง ช่วงวันที่ที่ไม่ว่าง และชื่อผู้เช่าเดิม** |
| 409 | สั่งปิดสัญญาที่ปิดไปแล้ว | บอกว่าสัญญานี้สิ้นสุดไปแล้ว |

409 ตอนสัญญาทับกันสำคัญที่สุด เพราะ US-05-S1 เขียนไว้ว่าต้อง
"แสดงข้อความบอกชัดเจนว่าห้องไม่ว่างในช่วงวันที่ใด" ข้อความว่า "เกิดข้อผิดพลาด" เฉย ๆ ถือว่าไม่ผ่าน

ตัวอย่างที่หน้าเว็บคาดหวัง

```
ห้อง 102 ไม่ว่างในช่วง 2025-10-20 ถึง 2026-09-16 เพราะมีสัญญาของ ยูกิ ทานากะ อยู่แล้ว
```

## เรื่องที่ต้องระวังฝั่ง service

เช็คว่าทับกันไหมใน service ด้วย เพื่อให้ได้ข้อความที่คนอ่านรู้เรื่อง
แต่ **ห้าม** เอา service เป็นตัวกันจริง เพราะสองคำขอที่เข้ามาพร้อมกันจะเช็คผ่านทั้งคู่แล้วเขียนลงไปทั้งคู่
ตัวกันจริงคือ exclusion constraint จับ `DataIntegrityViolationException` ที่หลุดออกมาแล้วแปลงเป็น 409 ด้วย

นี่คือสิ่งที่ US-05-S2 ให้พิสูจน์ด้วย integration test ที่ยิงสองคำขอพร้อมกัน
ฝั่งหน้าเว็บกับ mock ทดสอบข้อนี้แทนไม่ได้ เพราะเป็น single thread ทั้งคู่

## ของที่ยังไม่ได้ตกลง

- ยังไม่มี endpoint ลบสัญญาถาวร ตอนนี้ใช้ปิดสัญญา (`terminate`) แทนทั้งหมด
  ประวัติสัญญาเป็นข้อมูลที่หอพักต้องเก็บอยู่แล้ว จึงไม่ควรลบทิ้งจริง
- `PUT /api/leases/{id}` ยังไม่ให้ย้ายสัญญาข้ามห้อง ถึงจะรับ `roomId` มาก็ตาม
  ถ้าจะทำเคสย้ายห้องจริง ต้องคุยกันก่อนว่านับเป็นสัญญาใหม่หรือแก้ของเดิม
