# สัญญา API ของใบเสร็จและเอกสาร PDF (billing)

เอกสารนี้คือข้อตกลงระหว่างฝั่งหน้าเว็บกับฝั่ง Spring Boot ว่า endpoint ของใบเสร็จ (US-10 / SSK-16)
เอกสารสัญญาเช่าเป็น PDF (US-11 / SSK-17) การส่งใบเสร็จทางอีเมล และการตั้งเวลาเตือนใบค้างรายเดือน (SSK-143)
หน้าตาเป็นแบบไหน

ต่างจาก [api-contract-lease.md](api-contract-lease.md) ตรงที่ฉบับนั้นเขียนขึ้น **ก่อน** ฝั่ง backend
ลงมือ เพราะหน้าเว็บทำไปก่อนแล้ว ส่วนฉบับนี้เขียนขึ้นพร้อมกับที่ backend ทำเสร็จ ตอนนั้นหน้า
Payment Management กับป็อปอัป Generate Receipt ฝั่งหน้าเว็บยังเป็นข้อมูลตัวอย่างจาก Figma
ล้วน ๆ (`frontend/src/pages/PaymentsPage.tsx` กับ `frontend/src/components/GenerateReceiptModal.tsx`)
รูปร่างข้อมูลในเอกสารนี้จึงถูกทำให้ตรงกับสิ่งที่สองไฟล์นั้นวาดไว้อยู่แล้ว
**ตอนนี้หน้าเว็บต่อ API ครบแล้ว** (PR #116 และ SSK-16) ดูหัวข้อ "หน้าเว็บที่ต่อแล้ว" ข้างล่าง

## กฎข้อเดียวที่สำคัญที่สุดของเอกสารนี้ (US-16-S3)

**ใบเสร็จเก็บ snapshot ของอัตราที่ใช้ตอนออกใบไว้ในตัวมันเอง และไม่เคยอ่าน `apartment_config`**

ทางเดินของอัตราหนึ่งชุดเป็นแบบนี้

```
apartment_config  --(คัดลอกตอนเซ็นสัญญา)-->  lease  --(คัดลอกตอนออกใบเสร็จ)-->  receipt
```

แต่ละลูกศรคือการ **คัดลอกค่าไปเก็บ** ไม่ใช่การอ้างอิงกลับ ผลคือ

- แอดมินขึ้นค่าไฟของตึกวันนี้ สัญญาที่เซ็นไปแล้วไม่เปลี่ยนเงื่อนไข
- แอดมินแก้อัตราของสัญญาใบหนึ่ง (`PUT /api/leases/{id}`) ใบเสร็จที่ออกไปแล้วของสัญญาใบนั้น
  ไม่เปลี่ยนยอด
- ใบเสร็จที่พิมพ์ส่งผู้เช่าไปแล้ว เปิดดูในระบบอีกกี่ปีก็ยังเป็นยอดเดิม

ถ้าไม่ทำแบบนี้ วันที่ขึ้นค่าไฟ ใบเสร็จเก่าทุกใบจะเปลี่ยนยอดย้อนหลังพร้อมกัน ซึ่งผิดทั้งทางบัญชี
และทางกฎหมาย เพราะผู้เช่าจ่ายตามยอดที่พิมพ์ไปแล้ว

ตารางที่เก็บ snapshot คือ `receipt` ใน `V9__receipt.sql` คอลัมน์ `monthly_rent`,
`electric_rate_per_unit`, `water_rate_per_unit`, `common_area_fee`, `internet_fee`
เทสที่บังคับกฎข้อนี้ไว้คือ `ReceiptApiTest` เมธอด `changingApartmentRatesDoesNotTouchIssuedReceipts`
ซึ่งขึ้นอัตราของตึกจริง ๆ หลังออกใบแล้วอ่านใบเดิมกลับมาเทียบ

## ตารางที่เพิ่ม

`V9__receipt.sql` (V8 ถูกจองไว้ให้ตารางใบแจ้งซ่อมของ CR-05 แล้ว)

```sql
CREATE TABLE receipt (
    id         BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    receipt_no VARCHAR(20) NOT NULL,
    lease_id   BIGINT      NOT NULL REFERENCES lease (id),
    billing_month DATE     NOT NULL,

    electric_units NUMERIC(10, 2) NOT NULL,
    water_units    NUMERIC(10, 2) NOT NULL,

    -- snapshot ของอัตรา ดูหัวข้อข้างบน
    monthly_rent           NUMERIC(10, 2) NOT NULL,
    electric_rate_per_unit NUMERIC(10, 2) NOT NULL,
    water_rate_per_unit    NUMERIC(10, 2) NOT NULL,
    common_area_fee        NUMERIC(10, 2) NOT NULL,
    internet_fee           NUMERIC(10, 2) NOT NULL,

    electric_amount NUMERIC(10, 2) NOT NULL,
    water_amount    NUMERIC(10, 2) NOT NULL,
    total_amount    NUMERIC(10, 2) NOT NULL,

    issued_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    due_date   DATE        NOT NULL,
    status     VARCHAR(10) NOT NULL DEFAULT 'PENDING',
    paid_at    TIMESTAMPTZ,
    payment_method VARCHAR(50),

    CONSTRAINT receipt_no_uk           UNIQUE (receipt_no),
    CONSTRAINT receipt_lease_month_uk  UNIQUE (lease_id, billing_month),
    CONSTRAINT receipt_month_first_day_ck CHECK (EXTRACT(DAY FROM billing_month) = 1),
    CONSTRAINT receipt_units_ck   CHECK (electric_units >= 0 AND water_units >= 0),
    CONSTRAINT receipt_status_ck  CHECK (status IN ('PENDING', 'PAID')),
    CONSTRAINT receipt_paid_ck    CHECK ((status = 'PAID') = (paid_at IS NOT NULL))
);
```

สามเรื่องที่ห้ามพลาด

- `billing_month` เก็บเป็น **วันที่ 1 ของเดือนเสมอ** บังคับด้วย `receipt_month_first_day_ck`
  ถ้าไม่บังคับ ใบเสร็จของเดือนเดียวกันที่บันทึกคนละวันจะเล็ดลอด `receipt_lease_month_uk` ไปได้
  ส่วน API รับส่งเป็นสตริง `"YYYY-MM"` การแปลงสองทางอยู่ใน `ReceiptService` ที่เดียว
- ตัวกันออกใบซ้ำเดือนของจริงคือ `receipt_lease_month_uk` ไม่ใช่การเช็คในโค้ด
  การเช็คในโค้ดมีไว้ให้ข้อความที่ผู้ใช้เห็นอ่านรู้เรื่องเท่านั้น
- `status = 'PAID'` กับ `paid_at IS NOT NULL` ผูกกันด้วย constraint จะมีแถวที่จ่ายแล้ว
  แต่ไม่มีวันที่จ่ายไม่ได้ เพราะหน้าเว็บโชว์สองอย่างนี้คู่กันเสมอ

### V14 บันทึกการส่งอีเมล (SSK-143)

```sql
ALTER TABLE receipt ADD COLUMN last_sent_at TIMESTAMPTZ;
ALTER TABLE receipt ADD COLUMN sent_count   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE receipt ADD CONSTRAINT receipt_sent_ck
    CHECK (sent_count >= 0 AND ((sent_count > 0) = (last_sent_at IS NOT NULL)));
```

- เก็บแค่ "ส่งสำเร็จครั้งล่าสุดเมื่อไหร่" กับ "ส่งไปแล้วกี่ครั้ง" ไม่ได้ทำตารางประวัติการส่งแยก
  เพราะสิ่งที่แอดมินต้องรู้ตอนจะกดส่งมีแค่ว่าใบนี้เคยส่งหรือยัง ถ้าวันหนึ่งต้องรู้ว่าแต่ละครั้งส่งไปที่อีเมลไหน
  ค่อยเพิ่มตารางประวัติ
- `receipt_sent_ck` ผูกสองคอลัมน์ไว้ด้วยกันแบบเดียวกับ `receipt_paid_ck` จะมีใบที่นับว่าส่งแล้ว
  แต่ไม่มีเวลาที่ส่งไม่ได้

### V15 ตั้งเวลาเตือนใบค้างรายเดือน (SSK-143)

```sql
CREATE TABLE billing_schedule (
    id           SMALLINT    PRIMARY KEY,
    enabled      BOOLEAN     NOT NULL DEFAULT false,
    day_of_month INTEGER     NOT NULL,
    send_time    TIME        NOT NULL,          -- เวลาไทย
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT billing_schedule_single_row_ck CHECK (id = 1),
    CONSTRAINT billing_schedule_day_ck        CHECK (day_of_month BETWEEN 1 AND 31)
);
-- แถวเดียว ปิดไว้ วันที่ 25 เวลา 09:00

CREATE TABLE billing_schedule_run (
    id            BIGINT      GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    period        VARCHAR(7)  NOT NULL,         -- 'YYYY-MM' ตามเวลาไทย
    started_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    finished_at   TIMESTAMPTZ,
    sent_count    INTEGER     NOT NULL DEFAULT 0,
    skipped_count INTEGER     NOT NULL DEFAULT 0,
    failed_count  INTEGER     NOT NULL DEFAULT 0,
    error         VARCHAR(500),
    CONSTRAINT billing_schedule_run_period_uk UNIQUE (period),
    CONSTRAINT billing_schedule_run_period_ck CHECK (period ~ '^[0-9]{4}-(0[1-9]|1[0-2])$'),
    CONSTRAINT billing_schedule_run_counts_ck CHECK (sent_count >= 0 AND skipped_count >= 0 AND failed_count >= 0)
);
```

- `billing_schedule` ทำตามแบบ `apartment_config` คือมีแถวเดียวที่ migration ใส่ไว้ให้ ใช้งานได้แค่ดูกับแก้
- `billing_schedule_run` หนึ่งแถวต่อหนึ่งเดือน **`billing_schedule_run_period_uk` คือตัวกันสอง pod รันเดือนเดียวกัน**
  ดูหัวข้อ "รอบเตือนรายเดือนทำงานอย่างไร" ข้างล่าง แถวล่าสุดคือ `lastRun` ที่หน้าเว็บแสดง

## Endpoint

| Method | Path | ทำอะไร |
| --- | --- | --- |
| GET | `/api/receipts` | รายการใบเสร็จ ใบใหม่สุดขึ้นก่อน รับ query `leaseId`, `status`, `month` |
| GET | `/api/receipts/{id}` | ใบเสร็จใบเดียว |
| POST | `/api/receipts` | ออกใบเสร็จ ตอบ 201 |
| POST | `/api/receipts/{id}/pay` | บันทึกว่าชำระแล้ว ตอบ 200 |
| POST | `/api/receipts/send` | ส่งใบเสร็จที่เลือกทางอีเมลพร้อมไฟล์ PDF (SSK-143) ตอบ 200 พร้อมรายการที่ส่งแล้วกับที่ข้าม |
| GET | `/api/billing-schedule` | ค่าตั้งเวลาเตือนใบค้างรายเดือน พร้อมเวลารอบถัดไปและผลรอบล่าสุด (SSK-143) |
| PUT | `/api/billing-schedule` | แก้ค่าตั้งเวลา ตอบรูปเดียวกับ GET |
| GET | `/api/receipts/{id}/pdf` | ไฟล์ใบเสร็จ ตอบ `application/pdf` เป็นไฟล์แนบ |
| GET | `/api/leases/{id}/contract.pdf` | เอกสารสัญญาเช่าไว้เซ็น ตอบ `application/pdf` เป็นไฟล์แนบ |

ทุกตัวต้องล็อกอินก่อนเหมือน endpoint อื่นทั้งระบบ (ดูหัวข้อ "การเข้าสู่ระบบ" ใน
[api-contract-lease.md](api-contract-lease.md)) ไม่มี endpoint ลบใบเสร็จโดยตั้งใจ
ใบเสร็จที่ออกไปแล้วเป็นเอกสารทางบัญชี ถ้าออกผิดต้องออกใบใหม่ ไม่ใช่ลบของเดิมให้เลขที่หายไปจากลำดับ
เหตุผลเดียวกับที่สัญญาเช่าไม่มี endpoint ลบ

### body ของ POST /api/receipts

```json
{
  "leaseId": 1,
  "billingMonth": "2026-09",
  "electricUnits": 120,
  "waterUnits": 15,
  "dueDate": null
}
```

- `billingMonth` เป็นสตริง `"YYYY-MM"` ไม่ใช่วันที่เต็ม เพราะสิ่งที่ผู้ใช้เลือกคือเดือน
  ถ้าเป็นวันที่เต็ม สองฝั่งจะเดาไม่ตรงกันว่าต้องเติมวันที่เป็นอะไร
- `electricUnits` กับ `waterUnits` **บังคับทั้งคู่** ไม่ได้ตกไปเป็น 0 ให้เองเวลาไม่ส่งมา
  เพราะใบเสร็จที่ค่าน้ำค่าไฟเป็นศูนย์โดยไม่มีใครตั้งใจ คือใบที่หอเก็บเงินขาดทั้งเดือน
  โดยไม่มีอะไรฟ้อง (กฎเดียวกับที่ `terminate` บังคับ `endDate` แทนที่จะเดาวันนี้ให้)
- `dueDate` **ไม่บังคับ** ไม่ส่งมาให้ตกไปเป็น **วันที่ 5 ของเดือนถัดจากเดือนที่เรียกเก็บ**
  เช่นรอบบิล `2026-09` ครบกำหนด `2026-10-05`

### ใบเสร็จที่ตอบกลับ

```json
{
  "id": 1,
  "receiptNo": "RC-2026-0001",
  "leaseId": 1,
  "roomNumber": "103",
  "tenantName": "มานี รักเรียน",
  "tenantEmail": "manee.r@example.com",
  "billingMonth": "2026-09",
  "issuedAt": "2026-09-11T14:05:22.417Z",
  "dueDate": "2026-10-05",
  "status": "PENDING",
  "items": [
    { "item": "Room rent",       "detail": null, "usageValue": null,  "usageUnit": null,    "rate": null, "amount": 3500.00 },
    { "item": "Common area fee", "detail": null, "usageValue": null,  "usageUnit": null,    "rate": null, "amount": 350.00 },
    { "item": "Internet",        "detail": null, "usageValue": null,  "usageUnit": null,    "rate": null, "amount": 0.00 },
    { "item": "Electricity",     "detail": null, "usageValue": 120.00, "usageUnit": "units", "rate": 9.50,  "amount": 1140.00 },
    { "item": "Water",           "detail": null, "usageValue": 15.00,  "usageUnit": "units", "rate": 20.00, "amount": 300.00 }
  ],
  "totalAmount": 5290.00,
  "paidAt": null,
  "paymentMethod": null,
  "lastSentAt": null,
  "sentCount": 0
}
```

- `tenantEmail` คืออีเมลของผู้เช่าตามสัญญาของใบนี้ เป็น `null` ได้เพราะช่องอีเมลไม่บังคับ
  ป็อปอัป Send Invoices ใช้บอกล่วงหน้าว่าใบไหนจะถูกข้าม โดยไม่ต้องไปโหลดรายชื่อผู้เช่ามาเทียบเอง
- `lastSentAt` กับ `sentCount` คือเวลาที่ส่งอีเมลใบนี้สำเร็จครั้งล่าสุดกับจำนวนครั้งที่ส่งสำเร็จ (SSK-143)
  ยังไม่เคยส่งเป็น `null` กับ `0`
- `receiptNo` รูปแบบ `RC-<ปี ค.ศ.>-<ลำดับ 4 หลักของปีนั้น>` ขึ้นปีใหม่กลับไปเริ่มที่ `0001`
- `items` มีห้าบรรทัดเสมอ เรียงคงที่ตามด้านบน **บรรทัดที่ยอดเป็นศูนย์ก็ยังส่งมา** เพราะใบเสร็จ
  ต้องอ่านแล้วรู้ว่ารายการนั้นคิดเท่าไหร่ การซ่อนบรรทัดศูนย์ทำให้ผู้เช่าแยกไม่ออกว่าหอไม่คิดเงิน
  หรือระบบลืมคิด
- รูปของหนึ่งบรรทัดตรงกับ `ReceiptLineItem` ใน `GenerateReceiptModal.tsx` ทุกช่อง ยกเว้นช่อง `id`
  ที่ฝั่งหน้าเว็บใช้เป็น key ของ React ให้ใช้ `item` เป็น key แทนได้ เพราะชื่อทั้งห้าไม่ซ้ำกัน
- `detail` ตอนนี้เป็น `null` ทุกบรรทัด มีไว้เผื่อบรรทัดที่ต้องอธิบายเพิ่ม เช่นค่าเครื่องใช้ไฟฟ้า
  (US-17) หรือค่าซ่อมที่เรียกเก็บผู้เช่า (CR-05) ซึ่งยังไม่ได้ทำ ดูหัวข้อ "ที่ยังไม่มีในเฟสนี้"
- `usageValue` กับ `rate` เป็น `null` สำหรับบรรทัดเหมาจ่าย หน้าเว็บโชว์เป็นขีดกลาง
  ซึ่ง `GenerateReceiptModal.tsx` ทำอยู่แล้ว
- ยอดเงินทุกตัวปัดครึ่งขึ้นเหลือสองตำแหน่ง **ทีละบรรทัดก่อนนำไปรวม** ผลบวกของบรรทัดที่พิมพ์
  จึงเท่ากับยอดรวมที่พิมพ์เสมอ ผู้เช่ากดเครื่องคิดเลขตามแล้วต้องได้เลขเดียวกัน

สูตรคิดยอดรวม

```
totalAmount = monthlyRent + commonAreaFee + internetFee
            + (electricUnits x electricRatePerUnit)
            + (waterUnits   x waterRatePerUnit)
```

อัตราทั้งหมดมาจาก **สัญญา** ไม่ใช่จาก `apartment_config`

### body ของ POST /api/receipts/{id}/pay

```json
{
  "paymentMethod": "โอนผ่านธนาคาร"
}
```

`paymentMethod` ไม่บังคับ และ **ไม่ต้องส่ง body มาเลยก็ได้** หอนี้รับเงินสดหน้าเคาน์เตอร์เป็นหลัก
ซึ่งไม่มีอะไรให้ระบุ ถ้าบังคับ สิ่งที่จะได้คือคำว่า "-" ทุกใบ ซึ่งแย่กว่าปล่อยว่าง
ค่าที่เป็นช่องว่างล้วนถูกเก็บเป็น `null` กฎเดียวกับอีเมลของผู้เช่า

ตอบกลับเป็นใบเสร็จก้อนเดิมที่ `status` เป็น `PAID` และมี `paidAt` แล้ว

### body ของ POST /api/receipts/send (SSK-143)

```json
{
  "receiptIds": [3, 4]
}
```

ตอบ 200 แม้จะมีบางใบถูกข้าม เพราะคำขอทำงานครบตามที่ขอ ส่วนใบไหนออกไม่ได้ให้ดูใน `skipped`

```json
{
  "sent": [
    {
      "receiptId": 3,
      "receiptNo": "RC-2026-0003",
      "tenantName": "สมชาย ใจดี",
      "email": "somchai.j@example.com",
      "sentAt": "2026-09-26T02:14:05.123Z",
      "sentCount": 1
    }
  ],
  "skipped": [
    { "receiptId": 4, "receiptNo": "RC-2026-0004", "tenantName": "Kenji Watanabe", "reason": "NO_EMAIL" }
  ]
}
```

- ส่งตามลำดับที่ขอ id ซ้ำถูกตัดเหลือตัวแรก ส่งได้ไม่เกิน 100 ใบต่อคำขอ เพราะทุกใบต้อง render PDF
  คำขอที่ใหญ่เกินจะค้างนานจนหน้าเว็บคิดว่าพัง
- ถ้ามี id ไหนไม่พบ ตอบ 404 และ **ไม่มีใบไหนถูกส่งเลย** ผู้ใช้จะได้ไม่ต้องเดาว่าส่งไปแล้วกี่ใบ
- ส่งได้ทั้งใบ `PENDING` และ `PAID` ใบที่จ่ายแล้วส่งเป็นสำเนาใบเสร็จ หัวเรื่องบอกว่าจ่ายแล้ว
  ส่วนการเลือกว่าจะส่งใบไหนเป็นเรื่องของหน้าเว็บ (ดูหัวข้อ "หน้าเว็บที่ต่อแล้ว")
- `reason` ของใบที่ข้ามมีสองค่า
  - `NO_EMAIL` ผู้เช่าของใบนี้ไม่มีอีเมล
  - `SEND_FAILED` เมลเซิร์ฟเวอร์ปฏิเสธใบนี้ **หลังจากส่งใบก่อนหน้าในคำขอเดียวกันไปได้แล้ว**
- ถ้าเมลเซิร์ฟเวอร์ติดต่อไม่ได้ตั้งแต่ใบแรกที่จะส่ง ตอบ 503 ทั้งคำขอ ซึ่งแปลว่าไม่มีใบไหนออกไปเลย
  แต่ถ้าออกไปได้แล้วอย่างน้อยหนึ่งใบ ต้องตอบ 200 แล้วบอกใบที่เหลือเป็น `SEND_FAILED` ห้ามตอบ 503
  เพราะผู้ใช้จะเข้าใจว่าไม่มีอะไรออกไป แล้วกดส่งซ้ำให้ผู้เช่าได้อีเมลเดิมสองฉบับ
- ส่งสำเร็จแต่ละใบ `sentCount` เพิ่มหนึ่งและ `lastSentAt` เป็นเวลาที่ส่ง ส่งซ้ำได้เสมอและนับเพิ่มทุกครั้ง
  เพราะการส่งซ้ำ (เช่นผู้เช่าบอกว่าไม่ได้รับ) เป็นเรื่องปกติ แอดมินเห็นจำนวนครั้งก่อนกดอยู่แล้ว

### GET / PUT /api/billing-schedule (SSK-143)

body ของ PUT

```json
{
  "enabled": true,
  "dayOfMonth": 25,
  "sendTime": "09:00"
}
```

ทั้ง GET และ PUT ตอบรูปนี้

```json
{
  "enabled": true,
  "dayOfMonth": 25,
  "sendTime": "09:00",
  "updatedAt": "2026-09-26T02:00:00.000Z",
  "nextRunAt": "2026-10-25T02:00:00.000Z",
  "lastRun": {
    "period": "2026-09",
    "startedAt": "2026-09-25T02:00:00.512Z",
    "finishedAt": "2026-09-25T02:00:03.001Z",
    "sentCount": 2,
    "skippedCount": 1,
    "failedCount": 0,
    "error": null
  }
}
```

- `sendTime` เป็น `HH:MM` ตามเวลาไทย รับ `HH:MM:SS` ได้เหมือนเวลาแจ้งเตือนซ่อม แต่เก็บแค่ระดับนาที
- `dayOfMonth` 1 ถึง 31 เดือนที่สั้นกว่านั้นใช้วันสุดท้ายของเดือน เช่นตั้ง 31 เดือนกุมภาพันธ์ส่งวันที่ 28 (หรือ 29)
- `nextRunAt` คือเวลาที่งานจะส่งรอบถัดไป เป็น `null` ตอนปิดอยู่ คำนวณที่ server หน้าเว็บจึงโชว์ได้ตรงกับที่จะเกิดจริง
- `lastRun` คือรอบล่าสุดที่เคยรัน เป็น `null` ถ้ายังไม่เคยรัน `error` มีค่าเมื่อทั้งรอบส่งไม่ออกเลย (เช่น Mailpit ล่ม)
- `updatedAt` รูปแบบเดียวกับของ Apartment Config คือละเอียดระดับมิลลิวินาทีเสมอ

### เดือนที่อยู่นอกช่วงสัญญา

เทียบแบบ "เดือนนั้นทับกับช่วงของสัญญาไหม" ไม่ใช่ "อยู่ในช่วงเต็มเดือนไหม" เดือนแรกกับเดือน
สุดท้ายที่ผู้เช่าอยู่ไม่เต็มเดือนจึงออกใบได้ตามปกติ รวมถึงใบสุดท้ายของสัญญาที่ปิดไปแล้วด้วย
(สัญญาที่ `status` เป็น `ENDED` ยังออกใบของเดือนที่เคยอยู่ได้ แต่ออกของเดือนหลังย้ายออกไม่ได้)

ที่ต้องกันตั้งแต่ตอนออก เพราะ **ใบเสร็จที่ออกไปแล้วลบไม่ได้และแก้ไม่ได้** ไม่มี endpoint ลบ
โดยตั้งใจ ส่วนใบลดหนี้ยังไม่ได้ตกลงกัน (ดูหัวข้อ "ที่ยังไม่มีในเฟสนี้") ถ้าพิมพ์เดือนผิดแล้วระบบ
รับไว้ จะได้ใบที่เก็บเงินเดือนที่ผู้เช่าไม่ได้อยู่ ติดอยู่ในลำดับเลขที่ถาวรโดยไม่มีทางแก้

409 ของการออกใบซ้ำเดือนออกมาได้สองทาง คือทางที่ service เช็คเจอเอง กับทางที่สองคำขอ
เข้ามาพร้อมกันจนเช็คผ่านทั้งคู่แล้วไปโดน `receipt_lease_month_uk` ที่ database
**ทั้งสองทางตอบข้อความเดียวกันเป๊ะ** (`ApiExceptionHandler.constraintMessage` แปลชื่อ constraint
กลับเป็นประโยคเดียวกัน) ผู้ใช้สองคนที่เจอปัญหาเดียวกันจะได้ไม่เห็นคนละประโยค

### กดรับชำระสองครั้งพร้อมกัน

409 `This receipt has already been paid` ต้องออกแม้แต่ตอนที่สองคำขอเข้ามาพร้อมกัน (กดปุ่มรัว ๆ หรือเปิดหน้าเว็บ
ค้างไว้สองแท็บ) ไม่ใช่ปล่อยให้ใบหลังเขียนทับวันที่ชำระกับช่องทางการจ่ายของใบแรกแล้วตอบ 200
เพราะวันที่ชำระจริงคือข้อมูลที่ใช้ยืนยันกับผู้เช่าตอนมีปัญหา ถ้าหายไปจะไม่มีใครรู้ตัว

ตัวกันจึงเป็นการล็อกแถวที่ database (`SELECT ... FOR UPDATE` ผ่าน
`ReceiptRepository.findForUpdateById`) ไม่ใช่การเช็คสถานะในหน่วยความจำอย่างเดียว
คำขอที่สองจะรอจนคำขอแรก commit แล้วค่อยอ่าน ซึ่งตอนนั้นเห็นสถานะเป็น `PAID` แล้ว
เทสที่บังคับข้อนี้คือ `ReceiptApiTest.concurrentPaymentsMarkTheReceiptPaidExactlyOnce`
ซึ่งยิงสองคำขอพร้อมกันจริงแล้วดูว่าได้ 200 กับ 409 อย่างละหนึ่ง

### เลขที่ใบเสร็จซ้ำกัน ไม่ใช่ 409

เลขที่มาจากการนับใบของปีนั้นแล้วบวกหนึ่ง สองคำขอที่เข้ามาพร้อมกันจึงนับได้เลขเดียวกันทั้งคู่
ตัวกันซ้ำจริงคือ `receipt_no_uk` เมื่อชนที่ constraint นี้ **ฝั่ง backend ออกเลขใหม่ให้ใบที่แพ้
แล้วบันทึกอีกครั้งเอง** (ลองได้สูงสุด 5 รอบ) ไม่โยน error ใส่ผู้ใช้ เพราะการที่คนอื่นออกใบเสร็จ
พร้อมกันไม่ใช่ความผิดของคำขอนี้ และใบนี้ยังออกได้อยู่ แค่ต้องเปลี่ยนเลข

การลองใหม่ต้องเกิดนอก transaction ที่เพิ่งพัง `ReceiptService` จึงใช้ `TransactionTemplate`
แบบ `REQUIRES_NEW` ต่อหนึ่งรอบ ไม่ได้ใช้ `@Transactional` บนเมธอด `create` ถ้าดักแล้ววนลูป
อยู่ใน transaction เดิม คำสั่งรอบถัดไปจะพังด้วย `UnexpectedRollbackException` ซึ่งคนละเรื่อง
กับสาเหตุจริงและไล่หายาก

## เอกสาร PDF

เลือกทาง Thymeleaf render XHTML ออกมาก่อน แล้ว openhtmltopdf แปลงเป็น PDF
รายละเอียดการทำงานกับข้อควรระวังอยู่ใน README หัวข้อ "การออกเอกสาร PDF"
และในคอมเมนต์ของ `backend/src/main/java/com/sakurasoul/apartment/pdf/PdfRenderer.java`

| endpoint | ชื่อไฟล์ที่ผู้ใช้ได้ | เนื้อหา |
| --- | --- | --- |
| `GET /api/receipts/{id}/pdf` | `RC-2026-0001.pdf` | ใบเสร็จหนึ่งใบ หัวหอ เลขที่ ผู้เช่า ห้อง รอบบิล วันครบกำหนด ตารางห้าบรรทัด ยอดรวม สถานะการชำระ ช่องเซ็นสองฝ่าย |
| `GET /api/leases/{id}/contract.pdf` | `lease-contract-1.pdf` | สัญญาเช่า ชื่อผู้เช่า เลขบัตร Line ID เบอร์โทร เลขห้อง ชั้น วันเริ่ม/สิ้นสุด ค่าเช่า รอบบิล เงินประกัน อัตราที่ล็อกไว้สี่ตัว ช่องเซ็นสองฝ่าย วันที่ออกเอกสาร |

ทั้งสองตัวตอบ header

```
Content-Type: application/pdf
Content-Disposition: attachment; filename="RC-2026-0001.pdf"
```

เป็น `attachment` ไม่ใช่ `inline` เพราะปุ่มที่หน้าเว็บกดคือ Download
เอกสารทั้งสองใบพิมพ์เป็นภาษาอังกฤษ วันที่เขียนแบบ `11 Aug 2026` ตรงกับ `DISPLAY_DATE`
ใน `frontend/src/format.ts` และยอดเงินเป็นเยน `¥3,500` ไม่มีทศนิยม ตรงกับ `yenAmount`
การแปลงเกิดขึ้นตรงจุดพิมพ์อย่างเดียว (`pdf/DocumentFormat.java` เดิมชื่อ `ThaiFormat`)
ฟอนต์ Sarabun ยังฝังอยู่เหมือนเดิม เพราะชื่อผู้เช่ายังเป็นภาษาไทย

### เรื่องฟอนต์

README เขียนไว้ตอนแรกว่าจะใช้ **TH Sarabun New** แต่ของจริงใช้ตระกูล **Sarabun** จาก
Google Fonts แทน เป็นฟอนต์สายเดียวกัน (ออกแบบโดยคนเดียวกัน) ที่ต่างคือสัญญาอนุญาตเป็น
**SIL Open Font License 1.1** ชัดเจน จึงคอมมิตไฟล์ลง repo และแจกจ่ายไปกับ Docker image
ได้โดยไม่ต้องตีความสัญญาอนุญาตเอง

ไฟล์อยู่ที่ `backend/src/main/resources/fonts/` มีสามไฟล์คือ `Sarabun-Regular.ttf`,
`Sarabun-Bold.ttf` และ `OFL.txt` (ตัวสัญญาอนุญาต **ห้ามลบ**)

**ฟอนต์ต้องถูก embed ลงในไฟล์ PDF ไม่ใช่แค่ตั้ง `font-family`** ถ้าไม่ embed ตัวอักษรไทย
จะหายกลายเป็นช่องว่างหรือสระลอยผิดตำแหน่งเมื่อไปเปิดบนเครื่องที่ไม่มีฟอนต์นี้ ที่หลอกคือ
เปิดบนเครื่องตัวเองมักยังปกติ เทส `ReceiptApiTest` จึงเปิดไฟล์ที่ generate ออกมาด้วย PDFBox
แล้วไล่ดูชื่อฟอนต์ใน resource ของทุกหน้าว่ามี `Sarabun` อยู่จริง ไม่ได้เช็คแค่ว่าไฟล์เปิดได้

## การส่งใบเสร็จทางอีเมล (SSK-143)

ปุ่มส่งใบแจ้งหนี้ของ SSK-130 (#123) เคยเป็นแบบจำลองในหน้าเว็บล้วน คำถามสี่ข้อที่ถามผู้ดูแล requirement
ไว้ใน SSK-130 ไม่มีคำตอบ **หัวหน้าทีมจึงตัดสินแทนเมื่อ 26 ก.ย. 2569** ตามข้อเสนอเดิม

1. "ส่ง" คือส่งอีเมลจริงพร้อมไฟล์ PDF ใบเสร็จ เข้า Mailpit ที่รันอยู่ใน stack ของเราเอง
2. ผู้รับคือใบที่แอดมินเลือก หรือถ้าไม่เลือกเลยคือใบค้างทั้งหมดที่เห็นในตาราง ผู้เช่าที่ไม่มีอีเมลถูกข้ามพร้อมบอกเหตุผล
3. ตั้งเวลาเตือนใบค้างเดือนละครั้งฝั่ง backend ดูหัวข้อ "รอบเตือนรายเดือนทำงานอย่างไร" ข้างล่าง
4. บันทึกว่าแต่ละใบส่งไปแล้วเมื่อไหร่และกี่ครั้ง (`lastSentAt`, `sentCount`)

การออกบิลใหม่ให้ทุกห้องอัตโนมัติ **ยังทำไม่ได้** เพราะใบเสร็จต้องมีหน่วยน้ำไฟของเดือนนั้น และยังไม่มีตารางค่ามิเตอร์

### อีเมลไปที่ไหน

- วิชาห้ามใช้บริการภายนอก อีเมลจึงส่งเข้า **Mailpit** (`axllent/mailpit`) ซึ่งเป็น service หนึ่งใน
  docker compose และ k8s **ไม่ตั้ง relay** อีเมลทุกฉบับค้างอยู่ในกล่องของ Mailpit ไม่ออกนอกเครื่อง
- เปิดกล่องดูได้ที่ http://localhost:8025 (compose) ส่วนบน k8s ใช้
  `kubectl -n sakura-soul port-forward svc/mailpit 8025:8025` แล้วเปิด URL เดียวกัน
- backend ต่อ SMTP ตาม `SPRING_MAIL_HOST` / `SPRING_MAIL_PORT` (ค่าตั้งต้น `localhost:1025`)
  ผู้ส่งคือ `Sakura Soul Apartment <billing@sakura-soul.local>` เปลี่ยนที่อยู่ได้ด้วย `APP_MAIL_FROM`
- timeout ของ SMTP ตั้งไว้ 5 วินาที ถ้า Mailpit ไม่ตอบ คำขอจะได้ 503 ภายในไม่กี่วินาที ไม่ค้าง
- health indicator ของ mail ถูกปิด (`management.health.mail.enabled: false`) Mailpit ล่มต้องเห็นเป็น 503
  ตอนกดส่ง ไม่ใช่ทำให้ `/actuator/health` ของทั้งแอปแดง

### หน้าตาอีเมล

ภาษาอังกฤษเหมือนหน้าเว็บและ PDF เป็นข้อความธรรมดา (plain text) แนบไฟล์เดียวกับ `GET /api/receipts/{id}/pdf`
ทุกฉบับ ชื่อไฟล์คือเลขที่ใบเสร็จ ตัวเลขกับวันที่ใช้ `DocumentFormat` ชุดเดียวกับ PDF อีเมลกับไฟล์แนบจึงเขียนยอดตรงกันเสมอ

ใบที่ยังไม่จ่าย (`PENDING` รวมใบที่เลยกำหนดแล้ว)

```
Subject: Receipt RC-2026-0003 for Sep 2026 - ฿5,290.00 due 5 Oct 2026

Dear สมชาย ใจดี,

Please find attached receipt RC-2026-0003 for Sep 2026 (Unit 101).

Amount due: ฿5,290.00
Due date: 5 Oct 2026

If you have already paid, please ignore this email.

Sakura Soul Apartment
```

ใบที่จ่ายแล้ว (`PAID`) ส่งเป็นสำเนา ถ้าไม่ได้บันทึกช่องทางการจ่าย วงเล็บท้ายบรรทัด Paid on จะไม่มี

```
Subject: Receipt RC-2026-0001 for Aug 2026 - paid

Dear สมชาย ใจดี,

Please find attached a copy of receipt RC-2026-0001 for Aug 2026 (Unit 101).

Total: ฿5,290.00
Paid on 11 Sep 2026 (Cash)

Thank you for your payment.

Sakura Soul Apartment
```

### รอบเตือนรายเดือนทำงานอย่างไร

งาน `BillingScheduler` ตื่น **ทุกนาที** ตามเวลาไทย (`@Scheduled(cron = "0 * * * * *", zone = "Asia/Bangkok")`)
อ่านค่าตั้งเวลาแถวเดียว แล้วถามว่าถึงรอบของเดือนนี้หรือยัง ถ้าถึงก็ส่งเตือนแล้วจดว่าเดือนนี้ส่งแล้ว
ตื่นทุกนาทีเพราะเวลาที่แอดมินตั้งเป็นระดับนาที และการอ่านแถวเดียวต่อนาทีถูกมาก

**รอบของเดือนหนึ่ง** คือวันที่ `dayOfMonth` (หนีบเป็นวันสุดท้ายถ้าเดือนสั้นกว่า) เวลา `sendTime` ตามเวลาไทย
`nextRunAt` คิดแบบนี้

1. ปิดอยู่ ไม่มีรอบ
2. เดือนนี้ยังไม่เคยรัน **และ** รอบของเดือนนี้อยู่หลังเวลาที่กดบันทึกล่าสุด (`updatedAt`) รอบถัดไปคือรอบของเดือนนี้
   ถึงจะเลยเวลาไปแล้วก็ตาม ถ้าเลยแล้วงานจะส่งในนาทีถัดไป (กรณี backend ดับตอนถึงเวลาแล้วเพิ่งกลับมา)
3. นอกนั้นรอบถัดไปคือรอบของเดือนหน้า

ข้อ 2 ทำให้ **ค่าใหม่มีผลตั้งแต่รอบแรกหลังกดบันทึก** ถ้าวันนี้วันที่ 26 แล้วแอดมินเพิ่งเปิดใช้โดยตั้งวันที่ 25
ระบบจะไม่ส่งทันที แต่รอวันที่ 25 ของเดือนหน้า เปิดใช้ปุ๊บแล้วอีเมลออกทั้งตึกโดยไม่ตั้งใจแย่กว่ารอหนึ่งเดือน
ถ้าอยากส่งเดี๋ยวนี้ให้กด Send All Invoices แทน

**หนึ่งรอบส่งอะไร** ทุกใบที่ยัง `PENDING` (รวมใบที่เลยกำหนดแล้ว) ด้วยกฎชุดเดียวกับ `POST /api/receipts/send`
ใบที่จ่ายแล้วไม่ส่ง ผู้เช่าที่ไม่มีอีเมลถูกข้าม ผลของรอบเก็บใน `billing_schedule_run` แถวของเดือนนั้น

**สอง pod** k8s รัน backend สอง pod งานนี้จึงตื่นพร้อมกันสองตัวทุกนาที ตัวที่ถึงรอบก่อนต้องจองเดือนนั้นด้วยการแทรกแถว
`billing_schedule_run` ใน transaction ของตัวเองก่อนส่งอะไร ตัวที่แทรกไม่ผ่านเพราะ `billing_schedule_run_period_uk`
คือตัวที่แพ้ ข้ามไปเงียบ ๆ ผู้เช่าจึงได้เตือนเดือนละฉบับเดียว ไม่ใช้ ShedLock เพราะแถวนี้เป็นข้อมูลที่ต้องเก็บอยู่แล้ว
(รอบล่าสุดที่หน้าเว็บโชว์) และใช้วิธีเดียวกับตัวกันซ้ำอื่นของระบบ คือให้ constraint ของฐานข้อมูลเป็นด่านสุดท้าย

**สิ่งที่ตั้งใจไม่ทำ**

- ไม่ลองใหม่เอง ถ้าทั้งรอบส่งไม่ออกเพราะ Mailpit ล่ม แถวของเดือนนั้นเก็บ `error` ไว้และจะไม่รันซ้ำเองในเดือนนั้น
  หน้าเว็บโชว์ว่ารอบล่าสุดพัง แอดมินกด Send All Invoices ส่งเองได้ ส่วนการลองใหม่ทุกนาทีจะเขียน log เตือนไม่หยุดถ้าพังนาน
- ถ้า backend ดับยาวข้ามเดือน รอบของเดือนที่ข้ามไปจะหายไป เพราะข้อ 2 ดูแค่เดือนปัจจุบัน
- ถ้า pod ตายระหว่างส่ง แถวของเดือนนั้นค้างไว้โดยไม่มี `finishedAt` และเดือนนั้นไม่รันซ้ำ ใบที่ส่งไปแล้วถูกนับใน
  `sentCount` ของแต่ละใบอยู่แล้ว
- ไม่มี endpoint สั่งรันรอบเดี๋ยวนี้ เพราะถ้ามี มันต้องจองเดือนนั้นไปด้วย (รอบจริงจะไม่ออก) หรือไม่ก็ข้ามด่านกันซ้ำ
  การส่งเดี๋ยวนี้ใช้ `POST /api/receipts/send` อยู่แล้ว

## ที่ยังไม่มีในเฟสนี้

- **บรรทัดค่าเครื่องใช้ไฟฟ้ากับค่าซ่อม** ป็อปอัป Generate Receipt วาดไว้เป็นตัวอย่างสองบรรทัด
  (`Appliance fee`, `Repair charge`) แต่ยังไม่มีตารางรองรับ ต้องรอ US-17 (คลังอุปกรณ์)
  กับ CR-05 (ใบแจ้งซ่อม) ก่อน พอถึงตอนนั้นให้เพิ่มตาราง `receipt_item` แล้วต่อท้าย `items`
  รูปร่าง JSON ที่หน้าเว็บเห็นจะไม่เปลี่ยน เพราะเป็น array อยู่แล้วตั้งแต่วันแรก
- **การออกบิลอัตโนมัติทุกห้อง** ทำไม่ได้ เพราะใบเสร็จต้องมีหน่วยน้ำไฟของเดือนนั้นและยังไม่มีตารางค่ามิเตอร์
  ใบใหม่จึงยังออกทีละใบด้วยปุ่ม New Invoice
- **endpoint สรุปยอด** สำหรับการ์ดสามใบบนหน้า Payments
- **ใบลดหนี้ / การยกเลิกใบเสร็จ** ยังไม่ได้ตกลงกันว่าจะทำแบบไหน ตอนนี้ใบที่ออกแล้วแก้ไม่ได้เลย
- **ใบเสร็จของสัญญารายปี** ตอนนี้ทุกใบคิดเป็นหนึ่งเดือนเสมอ ถึงสัญญาจะเป็น `YEARLY` ก็ตาม
  ยังไม่ได้ตกลงกันว่ารอบบิลรายปีควรออกใบเสร็จหน้าตาแบบไหน
